## Approved decisions

### PR (a) design

- **Activity request.** `page_endpoint` turns an `activity` task into `repos/<repo>/actions/runs?per_page=30`, with no `status` (today: `?status=in_progress&per_page=100&page=1`, lines 77 and 82). It is still 1 request per check.
- **No `total` for activity.** `read_page` stops returning `total` for `activity`. The unfiltered `total_count` counts every run. The summary status pages (`in_progress`, `queued`, `waiting`, `pending`, `requested`) keep `total`, so #30's "+N more" row is unchanged. The condition at `actions.py` line 197 becomes `task.get("status") in ACTIVE`.
- **Catalogue.** Each repository gains `default_branch`, set to `plain(row.get("default_branch") or "")`. `Object.assign(existing, repo)` (`Polling.js` line 217) copies it.
- **A full page is partial.** On the unfiltered activity page, `partial` is also true when `total` is not a number and the page holds 30 runs (a full page). A missing unfinished run that is not `kept()` is then dropped with no lookup. A page with fewer than 30 runs holds the whole history, so a missing run is looked up as today.
- **Every unfinished status is reconciled on an unfiltered page.** A run with `status !== "completed"` that is missing from the page is treated the way a missing `in_progress` run is treated today. This applies only to the unfiltered `activity` task (see "Deviations needing approval", item 1).
- **No crash on trimmed runs.** `mergeRuns` trims completed runs to 10, then line 162 does `delete cached.awaitingFinal` on `runFor(...)`. For a trimmed run `runFor` is `undefined`, so a 30-completed-run page would throw. The loop must skip runs that are no longer cached.
- **`r.active`.** For an activity page with no `total`, it is the number of `in_progress` runs on the page (line 163, unchanged). `r.hidden.in_progress` is written only when `total` is a number, so only from the summary path.
- **`r.last`.** `lastResult(r, runs, now, page, size)` in `Polling.js`:
  1. If `r.last` exists and `r.last.branch !== r.default_branch`, clear it. If `r.default_branch` is empty, return after clearing.
  2. Candidates: `status === "completed"` and `head_branch === r.default_branch`. Take the one with the highest `id`.
  3. Replace `r.last` with `{id, conclusion, at: run.updated_at, url: run.html_url, branch: r.default_branch, confirmedAt: now}` when there is no `r.last`, or the id is higher, or the id is equal and `updated_at` is not older (if either date does not parse, treat it as not older). An older id never replaces a newer one. With no candidate, `r.last` is kept.
  4. **`confirmedAt` is the stale clock, not `r.activityAt`.** A page confirms `r.last` (sets `confirmedAt = now`) only if it holds a qualifying run, or it reaches back past `r.last`: `page.length < size`, or some run on `page` has `id <= r.last.id`. Callers pass `page = null` when there is no page to reason about, which means no reach.
  5. It is called from three places: `activity()` when the page is unfiltered (`page` = the items, `size` = 30), the end of the summary snapshot (`runs` = `t.all`, `page` = the `recent` phase items, `size` = 10), and the single-run lookup in `complete()` (`runs` = `[resolved]`, `page` = null). It is never called from the summary's `in_progress` phase: that page holds only in-progress runs, so it would falsely look as if it reached back.
  6. It runs before `mergeRuns` and before the snapshot's `recent(...)`, so the new last-result run is protected when the list is trimmed.
- **Catalogue refresh clears a stale result.** In the catalogue branch of `complete()`, when `existing.default_branch !== repo.default_branch` (before `Object.assign`), delete `existing.last`. The row never shows a result for a branch that is no longer the default.
- **`kept()`** also returns true when `r.last && run.id === r.last.id`. This is the single place that decides what is never dropped.
- **Row text** (`ActionsModel.js` `rows()`), in this order:

| Repository state | `status` | `info` |
| --- | --- | --- |
| archived / disabled | `neutral` | `archived` / `disabled` |
| `repo.error` | `error` | `unavailable` |
| not checked (no `checked`, no `runs`) | `neutral` | `not checked` |
| last result is a failure | `failure` | `✕ 3h · 2 running` |
| last is success, checked within 30 min | `success` | `✓ 3h · 0 running` |
| last is success, check older than 30 min | `neutral` | `✓ 3h · 0 running · stale` |
| other result (cancelled, skipped, neutral) | `neutral` | `⊘ 3h · 0 running` |
| checked, no default-branch run held | `neutral` | `no result · 0 running` |

  - "Checked within 30 min" is `now - r.last.confirmedAt < 1800000` (3 idle intervals). A failure stays `failure` when stale and gets the same ` · stale` suffix.
  - The age is `ago(r.last.at, now)`: under 60 s `Ns`, under 3600 s `Nm`, otherwise `Nh` (floor). It reads `3h`, not `3h ago`.
  - The state and age come first, so an elided tail loses the running count or "stale" before the result.
- **Sort.** Rank 0 is `status === "failure"`, rank 1 is `active > 0`, rank 2 is everything else (archived, disabled, unavailable, not checked). Within rank 1 the order is most running first (today's order). Rank 0 and rank 2 keep catalogue order. Nothing is sorted by time. The array sort is stable, as the existing code assumes.
- **Placeholder** (`ActionsPanel.qml` line 293): "running first" becomes "failing, then running first". After the rebase, use #42's version of the string and add the words "failing, then".
- The delegate (`ActionsPanel.qml` lines 321-358), `statusColor` (line 166), `icon()` and `shownFields` (`ActionsModel.js` line 93) need no change. The repo row still only uses `title`, `subtitle`, `status`, `info`. If a step adds a field the delegate reads, add it to `shownFields`.

### PR (b) design

- **`actor_login`.** The helper adds `row["actor_login"] = plain(row["actor"]["login"])` when `row["actor"]` is a dict with a string `login`, else `""`. It does this for run-list rows (line 192) and for the single-run reply (line 182). The panel searches `actor_login`, never `actor`.
- **Search tokens.** `rows()` splits the filter on whitespace. A word `branch:<x>`, `actor:<x>` or `is:failed` with a non-empty value is a token, case-insensitive. Everything else is plain text, matched as today (repository name and description, run name, title, branch and state). An unknown prefix (`is:open`, `foo:bar`) and an empty value (`branch:`) are plain text. If there are no tokens, behaviour is exactly today's.
  - `branch:<x>`: run `head_branch` contains `<x>`. `actor:<x>`: run `actor_login` contains `<x>`. `is:failed`: run `conclusion` is in the failed list.
  - AND of all tokens and the plain text. A repository shows if at least one held run matches every token. A repository-name match does not lift the token filter. Plain text in the same query must still match the repository or the run.
  - No new requests. Filters apply only to held runs, so an unchecked repository cannot match a token.
  - With tokens present the `more` row is not shown.
- **Load more.** `m` raises `r.recentLimit` (default 10) for the selected repository by 30, up to 100.
  - `recent()` uses `r.recentLimit || 10` instead of the literal 10. The `recent` summary phase and the new task both ask for `per_page=<limit>`.
  - New task kind `more`, key `more:<repo>:`, group `interactive`, fetching only the `recent` page, 1 request. Its completion only calls `mergeRuns` and sets `r.recentFetched`. It touches no `hidden`, `summaryAt` or unfinished runs.
  - `m` does nothing while a `more` task or a `summary` task exists for that repository. The limit is raised only when a task is created.
  - `page_endpoint` accepts an optional `limit` for `recent`: an `int` from 1 to 100 (a bool, string or float is rejected), else `ValueError("Invalid page limit")`. The default stays 10. It is built into the endpoint from the validated integer.
  - The panel line is `last 10 runs fetched · m loads 30 more`, shown only when `r.recentFetched >= (r.recentLimit || 10)`. At 100 it reads `last 100 runs fetched`. It is joined with the hidden-count parts (` · `) into the one existing `more` row. A repository never has two.
  - `m` is free (the panel uses `j k h l r R o /`, Esc, and after #42 `y ? g G`). It goes into `keybindings.sh` and the README key table.

### Request cost

An idle repository is 6 requests an hour before and after, and a repository with a running workflow is 240 an hour before and after. The selected repository is unchanged. `m` is 1 request each. The response is larger: `per_page=30` of `NixOS/nixpkgs` was 422 KB when measured, and a typical small repository was not measured. The page is 30, not 100, because 100 was about 1.41 MB. If bandwidth hurts, `per_page` is one number to lower.

## Deviations needing approval

These need an owner answer before implementation. Approving this plan approves the stated default for each; delete or amend an item before approving to change it. Items 3, 4 and 5 differ from the spec's table or wording and are the ones to read.

1. **Unfinished-run reconciliation must be limited to the unfiltered `activity` task.** The spec says the loop treats any `status !== "completed"` run missing from the page the same way. The summary's `in_progress` phase also calls `activity()` with a page that holds only in-progress runs, so a cached `queued` run would be wrongly marked `awaitingFinal` (an unbudgeted lookup) or dropped. The plan adds the `unfiltered` flag (step 2) and keeps the summary path as it is. The same flag keeps `lastResult` from running on that filtered page (step 3).
2. **Running icon.** The spec's row table gives `success` or `neutral` for a repository whose last result is not a failure, even when it has running workflows, so the ◷ icon no longer appears on a repository row, only "N running" in the text. The plan follows the table. The alternative is `in_progress` for a non-failing repository with `active > 0`.
3. **Stale suffix on other results.** The table gives ` · stale` only for success and failure. The plan applies it to every result so there is one code path. A cancelled result older than 30 minutes reads `⊘ 3h · 0 running · stale`.
4. **"No result" and staleness.** The spec says the "no result" row uses `r.activityAt`. The table has no stale variant of it, so the plan shows `no result · N running` for any checked repository with no default-branch run, with no suffix. `checked` is set when an activity check succeeds, as today.
5. **Fetched-count row placement.** The spec says the line comes after the last run, but the existing `more` row sits before the first completed run. The plan keeps the existing position when a hidden-count part exists, and puts the row at the end when the fetched-count text is the only part. It is one row either way.
6. **Age format.** `ago()` has no day unit, so a result from 3 days ago reads `72h`. This matches the spec's "same seconds/minutes/hours rule" and its short column.
7. **Memory.** After PR (a) every repository with activity holds up to 10 completed runs plus `r.last`, where today only running runs are held. The spec accepted this implicitly. If it matters on a 137-repository account, the cap in `recent()` for non-selected repositories is the one place to lower.
8. **`more` does not refresh the last result (a review finding, not applied).** The spec says the `more` completion only calls `mergeRuns`. If the newest 30 runs are all on other branches and the default-branch failure is run 31, `m` shows that failure in the run list while the repository row still reads `no result` until the next summary. Calling `lastResult(r, data, now, data, r.recentLimit)` in the `more` completion would fix it at the cost of widening the spec's "touches nothing else" rule. The plan keeps the spec. Owner to decide.
