# Plan: Large repositories keep the panel responsive

## Approved decisions

- **Fetch limit.** Summary status phases (`in_progress`, `queued`,
  `waiting`, `pending`, `requested`) and the activity check each fetch
  exactly one page of 100 runs. They never follow `Link: rel="next"`.
  Catalogue and jobs pages still follow it. Each snapshot costs 6 requests
  (up to 51 before), and each activity check costs 1 (up to 10 before).
  The scheduler, budget (at least 1 s apart, at most 60 a minute) and
  cooldown don't change.
- **Hidden count.** Each status page and activity page returns a top-level
  `total` field from `total_count`. It must be an `int >= 0`, otherwise a
  `ValueError` produces the existing `network` error. `total` isn't part of
  `data`, so PR #28's `okData` check, which requires `data` to be an array,
  still passes. `recent` pages don't return `total`.
  - Checked live on `NixOS/nixpkgs` on 2026-09-24:
    - Small counts are exact (26 queued, 4 in progress).
    - Counts above 1,000 are GitHub's estimate (three calls returned 412k,
      527k and 234k).
    - Status filters stop at 1,000 results: page 11 is empty.
- **Polling.**
  - `hidden[status] = max(0, total - data.length)`. A summary collects this
    in `t.hidden` and publishes it to `r.hidden` only when the snapshot
    completes. An activity check updates `r.hidden.in_progress`.
  - `r.active` comes from `total` when the reply has it.
  - A reply without `total` behaves as it does today: nothing hidden, and
    `r.active` counts the runs returned. The `tests/qml-smoke.py` fake
    helper depends on this.
- **Runs that are never dropped.** The single cap helper `recent()` from #31
  keeps expanded runs, `awaitingFinal` runs and now the inspected run
  (`r.repo === s.selected && String(run.id) === s.inspected`). This change
  is made once, in `recent()`. **Found in step 0:** `recent()` filters only
  the runs it's given, and at the end of a snapshot it's given
  `union(t.all, keep)`. So `keep` in `complete()`, which today holds
  `awaitingFinal` and expanded runs, also gets the inspected run. Otherwise
  an inspected run past the first 100 is never passed to `recent()`.
- **Partial activity page** (`total > items.length`). A missing running run
  is marked `awaitingFinal` only if it's expanded or inspected. Other
  missing runs are removed from `r.runs` and counted as hidden. When the
  page is complete, the behaviour is unchanged.
- **The "more" row.** For an expanded repository with any hidden count,
  `rows()` adds one row after its last unfinished run and before its
  completed runs:
  - key `repo:<r>:more`, parent `repo:<r>`, kind `more`, depth 1
  - title such as `+1843 more queued · +12 more waiting`, with statuses in
    phase order. A count above 1,000 reads `+about N more <status>`.
  - subtitle `o opens GitHub`, empty `status` and `info`, `repo` set,
    `url` `https://github.com/<r>/actions`, no `run`

  It's shown only when there's no search, or the search matches the
  repository. Search looks only at visible runs. `o`, `expand()` and the
  delegate already handle this row, so `ActionsPanel.qml` doesn't change.
- **`syncRows`.** It keeps the same signature and return value:
  1. Build an object of the new keys, then walk the model backwards and
     remove every row whose key isn't in it.
  2. Build an object of the model keys that are left.
  3. For each new row `i`: keep it if the key already matches, insert it if
     the key is missing, otherwise scan forward and `move` it to `i`.
  4. Call `setProperty` only when `title`, `subtitle`, `status` or `info`
     changed. A `ponytail:` comment says that this field list must follow
     the delegate.

  A key-lookup object is used instead of an index map kept up to date. The
  user approved this in the spec.
- **No new dependencies, settings, keys or QML changes.**
- **Order.** This lands after #26, #27, #28 and #31 are merged. It's
  measured against #27's one-second rebuild (`onNowChanged: rebuild()`).
