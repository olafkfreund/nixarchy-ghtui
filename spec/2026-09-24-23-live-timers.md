# Spec: Run and step timers tick every second

## Design

The duration text is already computed from `now`: `Model.rows(repos, expanded,
details, filterText, now)` in `rebuild()` (`ActionsPanel.qml:75`) calls
`duration(item, now)` (`ActionsModel.js:19-26`) for every run, job and step.
The 1 s `Timer` (`ActionsPanel.qml:202`) already updates `root.now`. Only the
connection between them is missing. The fix connects them.

Change `ActionsPanel.qml` only, two edits:

1. Next to `onFilterTextChanged` (line 38), add:

   ```qml
   onNowChanged: rebuild()
   ```

2. On the 1 s timer (line 202), add `triggeredOnStart: true`:

   ```qml
   Timer { interval: 1000; running: root.opened; repeat: true; triggeredOnStart: true; onTriggered: root.now = Date.now() }
   ```

   Without this, a panel reopened after a long time shows the durations from
   its last rebuild for up to one second, then they jump. With it, `now` is
   refreshed and the rows are rebuilt as soon as the panel opens.

`ActionsModel.js`, `Polling.js` and `actions.py` do not change.

### Why `rebuild()` keeps cursor, selection and scroll

The tick calls `rebuild()` with `resetSelection` undefined, so it takes the
path the poll replies already use through `adopt()`:

- **Selection and cursor:** `key` is the current row's key (line 70). A tick
  only changes the `info` text, so the keys and their order stay the same.
  `Model.selection(entries, key, cursor)` finds the same key at the same index
  and `cursor` keeps its value. `rebuild()` never calls `selectionChanged()`,
  so `Polling.select` does not run and no request is scheduled.
- **Delegates:** `syncRows` (`ActionsModel.js:77-98`) finds each key at its own
  index (no `insert`, `move` or `remove`). It calls `setProperty(i, "rowData",
  …)` only on rows whose JSON changed, which are the rows with a ticking
  duration. It returns `structureChanged === false`. Delegates are updated in
  place, not recreated.
- **Scroll:** when `structureChanged` is false, `rebuild()` does not touch
  `list.contentY` (lines 79-92). Delegate height depends only on `subtitle`
  (line 322), and a tick does not change the subtitle, so the layout does not
  shift.

No extra code is needed for these three.

### Which rows change

`duration()` uses `now` only when the item has a start time and no end time
(`completed_at`, or `updated_at` once `status === "completed"`). Completed items
keep a fixed string, so `syncRows` leaves them alone. Status comes from
`state(item)`, which reads only GitHub data, so a tick can never change a
status.

### CPU cost, and why there is no guard

The timer runs only while `root.opened`, so a closed panel does no work. That
meets the intent's "no work when it is closed" constraint without anything
new.

A tick runs `rows()` (sort the repositories, filter, build the rows) and
`syncRows()`. When the rows line up, which is always the case on a tick,
`syncRows` finds each key on the first comparison, so its cost is linear: one
`get` and two `JSON.stringify` calls per row. The O(n²) search happens only
when rows are inserted or moved, and a tick does neither. Measured in Node with
a synthetic worst case (150 repositories, all expanded, 10 runs each: 1650
rows), a tick takes about 7 ms. The normal view (137 repositories, a few
expanded) has about 150 rows and costs a small fraction of that. That is
about 0.7 % of one core in Node. QML's JavaScript engine is slower, so expect a
few times that in the worst case, and much less in normal use.

A guard such as "only when a visible row is running" would skip `rebuild()`
when nothing is ticking. It would add a scan of `entries` and a second place
that decides what "running" means, only to save work that already costs very
little. Leave it out, and name the limit in a comment on the `onNowChanged`
line:

```qml
// ponytail: full rebuild at 1 Hz (~7 ms at 1650 rows in Node); skip when no entry has an open-ended duration if it ever shows in a profile
```

## Alternatives rejected

- **Bind each delegate to `root.now`** (compute `Model.duration(...)` in the
  delegate's `info` binding). The delegate only has the flattened `rowData`,
  not the raw run/job/step with its timestamps, so the timestamps would have
  to be copied into every row. `rows()` would then no longer be the only place
  that builds the row text. It also re-evaluates every visible delegate's
  binding each second, running or not. That is more code and two sources of
  truth, compared with one line.
- **A separate duration model or ListModel role** (for example a
  `startedAt`/`endedAt` role plus a formatter in the delegate). This is the
  same drawback as above, plus a schema change to `visibleRows`, for a result
  `rebuild()` already produces.
- **Call `rebuild()` from the timer's `onTriggered` instead of `onNowChanged`.**
  The behaviour is the same, but it hides the dependency on `now` inside the
  timer. `onNowChanged` covers any future writer of `now` and lets the smoke
  test drive it synchronously by setting `panel.now` (see Verification).
- **Poll more often.** This breaks the "no extra GitHub requests" constraint
  and still jumps between replies.
- **Guard the rebuild (only while running or only when visible).** See CPU
  cost above: `running: root.opened` already covers "only when open", and the
  cost of a "running" guard is not justified.

## Risks

- **Cost with very large expanded trees.** The cost grows linearly with the
  number of visible rows. At 1650 rows it is about 7 ms per tick in Node, and
  slower in QML. If a user expands everything in a much larger account, the
  panel does more work each second. The `ponytail:` comment names the fix. No
  host-specific risk: it is the same QML on every machine.
- **Rows awaiting final status keep ticking.** A run the scheduler marked
  `awaitingFinal` still has `status: "in_progress"` and no `completed_at`, so
  its duration keeps going up until the single-run lookup returns. This is the
  last state GitHub reported, and the status text already says "awaiting final
  status", so it is acceptable.
- **Queued items with a start time.** A queued run that already has
  `run_started_at` ticks as well. `duration()` already does this today between
  replies, and the change only makes it visible every second.
- **`entries` reassigned every second.** `entries = next` re-evaluates
  bindings that depend on `entries` (`current`, the empty-list text,
  `status()`). All of them are cheap and none has side effects. `cursor` is
  assigned the same integer, which does not emit a change, so the
  selected-row highlight bindings do not re-run.

## Verification

1. **QML smoke test (fails today, passes after).** In `tests/qml-smoke.py`,
   in the stage-0 block, after `panel.adopt()` and `panel.move(1)` (the run
   row is selected, the panel is closed and nothing is polling), give the run
   a start time and check the tick:

   ```js
   panel.polling.repos[0].runs[0].run_started_at = new Date(panel.now - 5000).toISOString()
   panel.adopt()
   var key = panel.current.key, cursor = panel.cursor
   var scroll = JSON.parse(panel.status()).scrollY
   panel.now = panel.now + 3000
   check(panel.current.info === "8s", "running duration ticks with now")
   check(panel.current.key === key && panel.cursor === cursor, "tick keeps selection")
   check(JSON.parse(panel.status()).scrollY === scroll, "tick keeps scroll")
   ```

   Today the first `check` fails: `now` changes but nothing rebuilds, so
   `info` is still `"5s"`. After the change it reads `"8s"`. The later
   stage-0 checks (expand, collapse, filter) do not look at `info`, so the
   start time can stay on the run.

2. **Model test, no change needed.** `tests/model.cjs:21` already covers
   `duration()` with an explicit `now`, and lines 42-49 cover `syncRows`
   updating a changed row in place without a structure change, which is the
   path a tick takes.

3. **`nix flake check`** passes. It runs `tests/model.cjs`,
   `tests/polling.cjs` and the Python tests. The QML smoke test needs
   `quickshell` and the Omarchy theme, so it runs locally with
   `python3 tests/qml-smoke.py`, as the README describes.

4. **Runtime check.** Open the panel on a repository with a running workflow,
   expand the run and a job, move the cursor to a step, and scroll a little.
   For 20 seconds, the run, job and step durations go up by 1 s each second,
   and the cursor, highlighted row and scroll position do not move. Finished
   steps keep their durations. `panel.status().requests` goes up only as fast
   as it does without this change.
