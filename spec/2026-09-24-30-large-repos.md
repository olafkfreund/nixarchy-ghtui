# Spec: Large repositories keep the panel responsive

## Design

### Scope

The fix makes three changes:

1. The helper fetches at most one page of 100 runs for each status that isn't
   completed.
2. The panel shows one "+N more" row for the runs it didn't fetch.
3. `syncRows` becomes linear for the changes polling actually makes.

It adds no new files, dependencies, settings, keys or QML modules.
`ActionsPanel.qml` doesn't change. The existing `o` key and delegate already
handle the new row.

This lands after PR #27 (the one-second rebuild), and is measured against it.

### Checking against GitHub

These checks ran on 2026-09-24 with `gh api` against `NixOS/nixpkgs`:

- **`total_count` comes back with a status filter.**
  `actions/runs?status=queued&per_page=1` returned `total_count: 26` with one
  run. `status=in_progress&per_page=100` returned `total_count: 4` with four
  runs. For small counts, `total_count` matched the number of runs returned.
- **Past 1,000 results, `total_count` is an estimate.** Three calls to
  `status=completed` within a minute returned 412,491, 527,285 and 234,640.
- **Status filters stop at 1,000 results.** `status=completed&per_page=100&page=10`
  returned 100 runs and a `rel="next"` link. `page=11` returned 0 runs,
  `total_count: 0` and no `Link` header. Today's code follows that link, so
  it stops at 10 pages for each status without saying so.

### Helper: `actions.py` `read_page`

- **Only catalogue and jobs pages set `nextPage`.** Today every kind except
  `run` and `summary`/`recent` sets it (line 188). Summary status phases and
  the activity task (`in_progress`) now always return `nextPage: 0`.
  `page_endpoint` is unchanged, still `per_page=100&page=1`.
- **Activity and summary status pages return a `total` field.** This covers
  every status in `ACTIVE`. `total` is `body["total_count"]`, and must be an
  `int >= 0`. Otherwise the page raises `ValueError`, like the other shape
  checks, and becomes the existing `network` error.
  - `total` is a top-level field of the reply, not part of `data`. PR #28's
    `okData` check requires `data` to be an array for every kind except
    `run`, so `data` stays the list of runs.
  - `recent` pages don't return `total`.

This gives a fixed ceiling on requests:

| Request | Today | After |
| --- | --- | --- |
| One summary snapshot | `1 + Σ max(1, ⌈n/100⌉)`, up to 51 (10 pages per status) | 6 |
| One activity check | `max(1, ⌈n/100⌉)`, up to 10 | 1 |

The old whole-operation modes (`summary`, `activity`) aren't used by the
panel. They stay unchanged.

### Polling: `Polling.js`

- **Hidden counts.** In `complete()`, when a summary status page or an
  activity page succeeds, record
  `hidden[status] = max(0, reply.total - data.length)`.
  - A summary task collects these in `t.hidden`. Only when the snapshot
    completes is `r.hidden = t.hidden` published, the same as the existing
    rule that only a complete snapshot replaces `r.runs`.
  - An activity check updates only `r.hidden.in_progress`.
- **`r.active` comes from `reply.total`** when the reply has one, instead of
  counting the runs returned. The repository row's "N running" stays
  accurate when more than 100 runs are running.
- **Runs that are never dropped.** Both cap filters (`mergeRuns`, lines
  136-138, and the snapshot end, lines 216-219) already keep a run that is
  expanded or `awaitingFinal`. They now also keep the inspected run
  (`r.repo === s.selected && String(run.id) === s.inspected`), so the
  selected run can't disappear from under the cursor.
- **A partial activity page.** When `total > items.length`, a running run
  that isn't on the page may still be running. Today `activity()` marks every
  missing in-progress run `awaitingFinal`, and each one then triggers its own
  run lookup. On a partial page:
  - Only runs that must be kept (expanded or inspected) are marked
    `awaitingFinal`.
  - The other missing runs are removed from `r.runs`. They're counted in
    `hidden.in_progress`.
  - When the page is complete, the behaviour is unchanged.

No new tasks, phases or timers are added. The scheduler, its budget and the
cooldown handling are unchanged.

### Rows: `ActionsModel.js`

**`rows()` adds a "more" row.** For an expanded repository with any
`hidden` count above zero, it adds one row after that repository's last
unfinished run, before the completed runs. The row is added only when there
is no search, or the search matches the repository. Search looks only at
visible runs, so a search that matches runs never shows the count.

The row looks like this:

```
{key: "repo:<r>:more", parent: "repo:<r>", kind: "more", depth: 1,
 title: "+1843 more queued · +12 more waiting", subtitle: "o opens GitHub",
 status: "", info: "", repo: <r>, url: "https://github.com/<r>/actions"}
```

- **Labels.** Each status with a count above zero gets one part, in phase
  order. A count above 1,000 reads "+about N more queued", because GitHub
  estimates it (see above). Smaller counts are shown exactly as of the last
  fetch, like every other value in the panel.
- **Keys.** `openBrowser()` already opens `current.url` for any
  `github.com` URL, so `o` works. `expand()` ignores kinds other than `repo`,
  `run` and `job`, and the delegate adds an arrow only for those kinds, so
  the row can't expand. Selecting the row selects its repository, because it
  has `repo` and no `run`.

**`syncRows(model, rows)` is replaced.** It has the same signature and the
same return value (whether the structure changed):

1. Build an object of the new keys. Walk the model backwards and remove every
   row whose key isn't in it.
2. Build an object of the model keys that are left.
3. For each new row `i`:
   - If `model.get(i).rowKey` already matches, keep it.
   - Else if the key isn't in the model, insert it.
   - Otherwise scan forward for the key and `move` it to `i`.
4. Call `setProperty` only when one of the fields the delegate reads has
   changed: `title`, `subtitle`, `status` or `info`. `key`, `kind` and
   `depth` are fixed by the key. `current` reads `entries`, not the model.
   A `ponytail:` comment records that this field list must follow the
   delegate.

The forward scan in step 3 only happens when a row that stays changes
position, for example a run that starts and jumps to the top. Removing rows
first stops a single removal from turning into a cascade of moves (see
below).

### Measurements

Node 26 on p620, medians, using an array stand-in for `ListModel` (the real
one only costs more for each operation). The test repository is expanded and
has N queued runs, each with `run_started_at`, plus 10 completed runs.
"Tick" is `rows()` followed by `syncRows` with a new `now`, which is what
PR #27 runs every second. The script is `bench2.cjs` in the session
scratchpad. It also checks that the new `syncRows` produces the same keys
and rows as a fresh build after reversing, filtering and reordering rows.

| Queued runs | Rows | Tick, before | Tick, after | One row removed near the top, before → after | One run moved to the top, before → after | Rows reversed, before → after |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 100 | 112 | 0.6 ms | 0.3 ms | 0.2 → 0.1 ms | 0.1 → 0.1 ms | 0.3 → 0.1 ms |
| 500 | 512 | 2.3 ms | 1.3 ms | 0.8 → 0.1 ms | 0.7 → 0.1 ms | 2.8 → 0.6 ms |
| 1,000 | 1,012 | 5.3 ms | 2.6 ms | 1.8 → 0.2 ms | 1.3 → 0.2 ms | 9.8 → 1.9 ms |
| 2,000 | 2,012 | 9.3 ms | 5.4 ms | 3.4 → 0.4 ms | 2.6 → 0.4 ms | 37.9 → 6.8 ms |
| 5,000 | 5,012 | 25.7 ms | 14.9 ms | 11.6 → 1.2 ms | 8.6 → 1.7 ms | 205.3 → 43.7 ms |

Model operations at 5,012 rows (these are what the real `ListModel` and
`ListView` pay for):

| Change | Before | After |
| --- | ---: | ---: |
| Nothing changed | 0 | 0 |
| One row removed near the top | 5,010 moves | 1 remove |
| One run moved to the top | 1 move | 1 move |

With both changes, the busiest repository that can be shown is 5 unfinished
statuses × 100 runs, plus completed runs and runs that must be kept. That's
about 512 rows, or 1.3 ms per tick.

The case in the issue, a backlog of 5,000 queued runs, now shows 100 queued
runs and one "more" row, 113 rows in all. Its tick drops from 25.7 ms to
about 0.3 ms, and each snapshot costs 6 requests instead of 15. Without the
cap, even the new `syncRows` still costs 14.9 ms at 5,000 rows, because
`rows()` itself takes 13 ms. So the fetch cap does most of the work, and the
`syncRows` change removes the cascades.

### PR #27 and PR #28

- **PR #27 (#23, live timers)** adds `onNowChanged: rebuild()`. This makes
  the tick above the steady-state cost every second. The design doesn't touch
  that line or the `Timer`, and `rebuild()` still calls `rows()` and
  `syncRows()` the same way.
  - This work lands after #27 and is rebased onto it.
  - The #27 `ponytail:` note about skipping ticks when no row has an
    open-ended duration isn't needed. The worst-case tick is now about 1 ms.
- **PR #28 (#24, helper errors)** adds an `okData` check to
  `Polling.complete` that requires `reply.data` to be an array for every kind
  except `run`. It also adds the `setup` errorType, and changes
  `Model.reply(stdout, code, requestId)`.
  - `total` is a separate reply field, so it passes `okData` unchanged.
  - A missing or invalid `total_count` stays a `network` error inside
    `read_page`. It doesn't stop polling like `setup`.
  - #28 touches `read_page`'s `except` clause and `main()`. This work
    touches the `nextPage` condition above that clause, so a conflict would
    be textual only.
  - `rows`/`syncRows` don't overlap `Model.reply`.
  - It works in either merge order with #28.

## Alternatives rejected

- **Fetch everything, limit only what's shown.** This keeps up to 51
  requests per snapshot and 10 per activity check for one repository. The
  approver chose the fetch cap.
- **Follow pagination up to GitHub's 1,000-result limit.** This costs up to
  10 requests for each status, for rows nobody scrolls through.
- **An index map from key to position that is kept up to date.** Every
  `insert` or `move` in a `ListModel` shifts the positions after it, so
  keeping the map correct costs as much as the scan it replaces. An object
  of keys, plus checking the position in place, answers "is it there?" in
  O(1). Removing rows first makes the common changes linear.
- **`JSON.stringify` comparison, or comparing every field.** The delegate
  reads four fields that can change. The other fields are fixed by the key.
- **A display cap with a "show more" row that raises it.** This needs state
  for each repository and more requests. The approver chose `o` to open
  GitHub.
- **Search across hidden runs.** Those runs were never fetched. The approver
  chose visible runs only.
- **Skip rebuilds on ticks where nothing changes (#27's note).** This
  doesn't help the per-page rebuild, and isn't needed once rows are capped.
- **Replace `ListModel` with a JS array model, or a paged view.** This is a
  larger change, and it recreates delegates, which is what `syncRows` exists
  to avoid.

## Risks

- **The runs you see are the newest 100 of each status.** GitHub lists
  newest first. With a backlog, the oldest queued runs, which are the next
  to start, are hidden. The "more" row gives the count, and `o` opens GitHub.
- **The count lags.** It's as old as the last snapshot (up to 60 s for a
  selected repository) or activity check (10–15 s). Above 1,000, it's
  GitHub's estimate and is labelled "about".
- **A partial activity page removes running runs** that fall past the first
  100 without looking each one up. They're counted in "+N more in_progress",
  and runs that must be kept still get their single lookup. When the page is
  complete, the behaviour is unchanged.
- **Stale field list.** If a later change makes the delegate read a new row
  field, rows won't update until that field is added to the `syncRows`
  comparison. The `ponytail:` comment and a model test cover this.
- **Merge order.** This touches `Polling.js` and `ActionsModel.js`. PR #28
  touches `complete()` and `reply()` in those files. Rebase whichever lands
  second, and run all the tests again.
- **Tests that assume paging.** `test_actions.py` checks `Link` parsing
  through an activity page, which will now return `nextPage: 0`. That test
  moves to a jobs page, so the checks on the pagination link are still
  tested.

## Verification

Use only the existing Node and Python tests:

- **`tests/test_actions.py`**
  - A summary status page and an activity page return `nextPage: 0`, even
    when there's a `rel="next"` link.
  - Both return `total` from `total_count`.
  - A missing or negative `total_count` gives the `network` error.
  - `recent` has no `total`.
  - The `Link` validation tests run on a jobs page.
- **`tests/polling.cjs`**
  - With fake replies of 2,000 queued runs (`total: 2000`, 100 runs), a
    selected summary snapshot starts exactly 6 requests.
  - `r.hidden.queued` is 1,900, published only when the snapshot completes.
  - An activity check starts 1 request, and `r.active` equals `total`.
  - A partial activity page doesn't mark runs that aren't kept as
    `awaitingFinal`. It does mark an expanded run and an inspected run.
  - Runs that are expanded, inspected or `awaitingFinal` survive both cap
    filters.
  - The existing scheduler workload checks (budget, spacing, fairness)
    still pass.
- **`tests/model.cjs`**
  - The "more" row appears after the unfinished runs and before the
    completed runs.
  - Its title shows the exact count below 1,000, and "about" above it.
  - It has the repository's Actions URL.
  - It's hidden under a search that matches only runs.
  - On a stub `ListModel` that counts operations, `syncRows`:
    - does 0 operations when nothing changes,
    - does 1 `remove` for one removed row,
    - does 1 `move` for one run moved to the top,
    - updates a row when `info` changes, and leaves it alone when only
      `url` changes,
    - ends with the same keys and data as a fresh build after random
      inserts, removals and reorders.
- **`tests/qml-smoke.py`** and `nix flake check` pass after rebasing onto #27.
- **Live check**
  - Run `python3 actions.py page '{"kind":"summary","repo":"NixOS/nixpkgs","status":"queued","page":1,"requestId":1}'`.
    It should return up to 100 runs, `nextPage: 0` and `total`.
  - On razer, open the panel, expand a busy repository, and check that
    scrolling and the one-second timers stay smooth, and that `o` on the
    "more" row opens the Actions page.
  - Record the request counts from `status()`.
- **Performance**
  - Run `bench2.cjs` again against the implemented `ActionsModel.js`. The
    "after" column should be within noise of the table above.
  - Put the table in the PR.
