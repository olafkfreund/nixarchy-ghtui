# Spec: CI drives the panel with real key presses

## Design

### Scope

CI gets a second job that starts the real panel in a headless Wayland compositor and presses real keys. It adds tests, stubs and one read-only panel method. No shipped behaviour changes. No new GitHub requests, tokens or settings.

It touches `tests/qml-smoke.py`, a new `tests/stubs/` folder, `flake.nix`, `.github/workflows/check.yml`, `README.md`, and `ActionsPanel.qml` (one new function, see "Layout check"). The rules stay: argument arrays, #32 sanitising, github.com pinned, no token storage, theme-native, keyboard-first.

### Owner decisions (binding, 2026-11-16)

1. **Stub `qs.Commons` and `qs.Ui` in the repo.** CI needs no copy of Omarchy.
2. **Real key events in a headless Wayland compositor.**
3. **A separate CI job, not inside `nix flake check`.**
4. **Layout failure means** a row outside the list, an empty (zero-height) list, or overlapping rows.
5. **Drop the old missing-directory check** at `flake.nix:80-83`.
6. **Keep #36's no-rerun rule** (`spec/2026-09-24-36-smoke-flake.md:106-108`).

### Stubs (decision 1)

The panel imports `qs.Commons` and `qs.Ui` (`ActionsPanel.qml:6-7`). The smoke test makes a temporary shell root and symlinks `Commons` and `Ui` into it from the real Omarchy tree (`tests/qml-smoke.py:23-24`). The stub version does the same from `tests/stubs/Commons` and `tests/stubs/Ui`, each with a `qmldir`.

Only what the panel reads is stubbed. I listed it from the current code:

- `Color`: `background`, `accent`, `urgent`, and `menu.{background,border,text,selectedBackground,selectedText}`.
- `Style`: `cornerRadius`, `gapsOut`, `space()`, `font.{body,caption,title,menuFamily}`, `spacing.{hairline,sm,md,panelPadding}`.
- `Border`: `surfaceSpec()`, plus whatever `BorderSurface` calls.
- `BorderSurface`: a plain `Rectangle` with the `content*Inset` properties and `padding`. The real one is in `Ui/BorderSurface.qml`; the stub drops the border overlay and keeps the inset arithmetic, so the layout maths stays the same shape.

Stub values are fixed, readable numbers (fixed colours, fixed pixel sizes). The test no longer needs `OMARCHY_PATH`, a theme in `~/.local/state/omarchy`, `fontconfig` or `shell.toml` (`tests/qml-smoke.py:16-17,52-58`). The `EXPECTED_BACKGROUND` theme check goes. The stub check that replaces it only proves that the stubs load and the panel reads them: the test asserts the singleton value, as today's check at `tests/qml-smoke.py:90` does. That alone would still pass if the card colour binding at `ActionsPanel.qml:221` were removed, so the spec does not claim it proves the binding. Where the panel exposes no way to read the card colour, that stays a stub-loading check only.

Cost, accepted by the owner: the stubs can drift from real Omarchy. Nothing in CI catches theme API drift. The owner's manual run on a real desktop before a release does. The README says so.

### Real keys in a headless compositor (decision 2)

- **Compositor: `sway` with `WLR_BACKENDS=headless`, `WLR_RENDERER=pixman`, `WLR_LIBINPUT_NO_DEVICES=1`.** It supports `wlr-layer-shell`, which the panel needs (`WlrLayershell.layer/keyboardFocus`, `ActionsPanel.qml:211-214`), and the virtual keyboard protocol.
- **Key sender: `wtype`.** It sends real key events through that protocol, to whichever surface the compositor has focused. Sway's output is a virtual one, so nothing reaches the owner's desktop even when the test runs locally. That meets the constraint "test input must never reach the owner's desktop".
- **Renderer: `QT_QUICK_BACKEND=software`** and `QT_QPA_PLATFORM=wayland`, so no GPU is needed.
- **Versions come from `flake.lock`.** The pin is the nixpkgs input at `flake.lock:9` (`nixos-unstable`), the same one `nix flake check` already uses, so no new flake input. The new tools are still extra packages fetched from that pin. The plan must record the `sway`, `wtype` and `quickshell` versions read from that locked input (for example `nix eval --inputs-from . nixpkgs#sway.version`); this spec states none, because an unpinned `nixpkgs#` evaluation does not prove what CI gets.

**Session bootstrap.** The test does not rely on runner session defaults. It creates a private `XDG_RUNTIME_DIR` (a fresh temporary directory, mode 0700), writes a minimal explicit sway config (one headless output, no bar, no autostart, no bindings that run commands), and starts sway with `-c` on that config and `WAYLAND_DISPLAY` unset so sway picks its own socket name inside the private directory. The test waits for that socket, then runs `quickshell -p <root>` and `wtype` with an environment built from scratch: the private `XDG_RUNTIME_DIR`, that socket as `WAYLAND_DISPLAY`, the Qt and wlroots variables above, and the `PATH` for the scenario. The caller's `WAYLAND_DISPLAY`, `HYPRLAND_*`, `SWAYSOCK` and `DISPLAY` are not passed on. Teardown runs on every exit path (success, failed assertion, timeout, exception): terminate quickshell and sway, kill after a short grace period, remove the temporary directory.

The Python test then drives the panel as below.

**Flow.** `shell.qml` (the temporary one the test writes) keeps seeding two repositories and one run like today. The Python side sends keys with `wtype`. The QML side only reports, through a state line written to the log on every change; the line is built from the panel's existing `status()` (`ActionsPanel.qml:60-65`), which already carries `opened`, `rows`, `filter`, `editing`, `selected`, `requests`, `lastRequest`, `inFlight` and `scrollY`. Python reads that line, so the QML no longer calls `panel.move()` or `panel.expand()` itself.

**Readiness before the first key.** `opened` is not enough: `open()` sets it before the deferred `Qt.callLater(keys.forceActiveFocus)` (`ActionsPanel.qml:49,52`), and it says nothing about the compositor having mapped the surface or given it keyboard focus. Before the first key the test waits for `opened`, then for sway to report the layer surface mapped and holding keyboard focus (`swaymsg -t get_tree`/`-t get_inputs` against the private socket), then sends one harmless probe key (`k` at the top row, which leaves `cursor` at 0) and waits for a state line that proves the key arrived. Only then do the key steps start. Every later step uses only state lines newer than the key it sent (a sequence number on the state line), so an old line cannot satisfy a new wait.

Keys covered, each asserted from the state after the key:

| Key | Handler | Asserted |
| --- | --- | --- |
| `j`, `Down`, `k`, `Up`, `Home`, `End` | `ActionsPanel.qml:239-244` | `cursor` and selected row key |
| `Right` / `Return`, `Left` | `:245-246` | row expands, then collapses (`entries.length`) |
| `/` | `:247` | `editing` is true (focus in the search field) |
| `Escape` in the search field | `:281-283` | filter cleared, `editing` false, panel still open |
| `Escape` in the list with a filter | `:236-238` | filter cleared, panel still open |
| `Escape` in the list, no filter | `:236-238` | `opened` false |
| `r` and `R` (Shift+R) | `:248-250`, `Polling.manual` at `Polling.js:41-42` | `r` queues a `summary` request for the selected repository; `R` queues a `catalogue` request |

`Polling.manual` with `r` calls `ensure(s, "summary", ...)` for the selected repository (`Polling.js:44-52`) and does not queue an activity request; `seed` even deletes a queued activity task when a summary exists for that repository (`Polling.js:70-73`). With `R` it only sets `discover`, and `seed` turns that into a `catalogue` task (`Polling.js:66`). So the assertions are: after `r`, a new `summary` request for the selected repository appears; after `R`, a new `catalogue` request appears.

The fake helper (`tests/qml-smoke.py:27-40`) appends one line per request (`kind`, `requestId`, `repo`) to a file. The refresh assertions read that file, so "both kinds of refresh" are proven by what actually ran, not by internal state. Unrelated automatic work must not satisfy them: before each of the two refresh keys the test waits until the request file has stopped growing and no request is in flight, records that baseline, sends the key, and then requires a request of the exact expected `kind` beyond the baseline.

**Focus handover.** Because keys go through the compositor, the exclusive-focus path (`ActionsPanel.qml:214`) and the deferred focus call in `open()` (`:43-52`) are exercised for real: if the surface never takes keyboard focus, the probe key never arrives and the run fails at the readiness stage. The owner's intent question 2 is answered: CI covers the focus handover. The panel source is not changed for this.

**Waits, not sleeps.** Each key waits for the expected state with a timeout. No step is widened to hide flakiness. The existing 25 s whole-run limit and 18 s stage timers (`tests/qml-smoke.py:70,157`) stay as they are, or get split per stage, not raised.

### Layout check (decision 4)

Today the test reads `panel.entries`, not what is drawn. The row delegates live inside `list`, an id the test shell cannot see from outside `ActionsPanel`. So the panel gets one read-only function next to `status()` (`ActionsPanel.qml:60`):

```qml
function layout() {  // test hook: geometry of the delegates that exist
    var rows = []
    for (var i = 0; i < list.count; i++) { var item = list.itemAtIndex(i); if (item) rows.push({i: i, key: entries[i].key, x: item.x, y: item.y - list.contentY, w: item.width, h: item.height}) }
    return JSON.stringify({listWidth: list.width, listHeight: list.height, count: list.count, rows: rows})
}
```

The test fails when:

- `listHeight` or `listWidth` is 0 while `entries.length > 0` (the zero-height list at `ActionsPanel.qml:305-306`).
- A row that should exist is missing. After each cursor move the delegate for the selected row must be in `rows`; the hook no longer lets a list with no delegates pass. `count` must equal `entries.length`.
- The selected row has `w <= 0` or `h <= 0`, or does not fit in the list in both directions: `x >= 0`, `x + w <= listWidth`, `y >= 0` and `y + h <= listHeight`. The selected row is always scrolled into view by `positionViewAtIndex` (`:95`). Rows that are partly scrolled out are expected and not a failure.
- Two rows overlap (`y[i] + h[i] > y[i+1]`).
- Any seeded row, visited by key one after another (`j` from `Home` to `End`), fails the checks above in turn, and the selected row after `End` then `Home` is inside the list.

The seeded data must be large enough that the list overflows the stub viewport, so scrolling is exercised: the fake serves enough runs for the first repository that its rows exceed `listHeight` at the stub font sizes (the test checks `contentHeight > listHeight` and fails with a clear message if not). Two repositories and one run alone would not prove that a row reached by key and scrolled into view is seen inside the panel.

That makes a nonzero row height alone insufficient: a seeded row must be reached by key and sit inside the list. No stored images (the owner did not pick that).

Why a function and not reading `Window` pixels: a pixel grab would need `grabToImage` plumbing and is fragile with fonts. The geometry is what the rule is about.

### Failure paths (intent outcome 5)

Two extra scenarios in the same file, using the same compositor:

- **Helper cannot start.** Run with `PATH` holding only `quickshell`, `sway`, `swaymsg` and `wtype`, no `python3`. The panel must reach `error === "python3 not found"`, `workerBusy` false, and a stopped poll (`polling.auth` true), with no further requests. This covers `ActionsPanel.qml:144-151` and `onRunningChanged` (`:202`), and the `setup` type from #24. The menu registration also uses `python3` (`:180-186`); its failure is only a log line, so it is allowed and not asserted.
- **Close while a request runs.** The fake does not finish by itself: it writes its pid, then blocks until it is signalled. The test waits until the pid file exists and the panel reports `inFlight`, then sends `Escape` during the request. It asserts `workerBusy` false, the pid is gone within the existing wait, and the request count does not rise afterwards. Because the fake cannot end on its own, a panel that failed to cancel would leave the pid alive and the run would fail. The test kills any leftover fake pid on every exit path. Mutation proof: removing `requestProc.running = false` from `close()` (`ActionsPanel.qml:57`) must make this scenario fail.

Both end in a state the test checks, as the intent asks.

### Failure messages (intent outcome 6)

Keep #36's stage naming (`tests/qml-smoke.py:75-79`). Every key step carries a label such as `key Escape in search field: expected editing=false got ...`. On timeout the script prints the stage, the last state line and the sway/quickshell output.

### Flake and CI (decisions 3 and 5)

- `checks.plugin` (`flake.nix:55-88`) loses the invalid-directory block (`:80-83`). That removes its only use of `tests/qml-smoke.py`. Everything else in the check stays, so `nix flake check` stays fast and works on p620 with no desktop.
- A new `devShells.default` in `flake.nix` lists `quickshell`, `sway` (which brings `swaymsg`), `wtype`, `python3`. It is the one place the tool set is named. (Smaller than a new package or app, and useful locally.)
- `.github/workflows/check.yml` gets a second job `qml-smoke` next to `check`: same `actions/checkout` and `install-nix-action` SHAs already there (`:19-20`), same `permissions: contents: read`, same 15 minute limit, step `nix develop -c python3 tests/qml-smoke.py`. No new action, no secret, no network call to GitHub.
- Two places must stay in step (flake devShell and the workflow). Both are one line each, and the workflow job calls the devShell, so the tool list is not duplicated.
- `tests/qml-smoke.py` keeps its optional `plugin_dir` argument, so the same script still tests the built `./result` (`README.md:195-205`).

### README

`README.md:205-207` ("the QML check runs only locally", "requires a graphical session, Quickshell and `OMARCHY_PATH`") is rewritten. It says the QML check runs in CI in a headless compositor on stubs, can be run locally with `nix develop -c python3 tests/qml-smoke.py`, and that the stubs do not follow Omarchy, so a real-desktop check before a release stays the owner's job.

### Rerun rule (decision 6)

No `retry`, no `continue-on-error`, no rerun step in the new job. A failing run is a failure. This restates and keeps #36 section 4. If the new job proves flaky on GitHub runners, the answer is to fix the wait, not to rerun. A change to this needs a new owner decision.

If #41 lands first, the fake helper may need its reply to include whatever the new gh-login check calls. Order: #47 can land before or after #41; whichever is second adjusts the fake.
- **#42 (Panel UI)** is the largest overlap. Land #47 first so #42's keys and accessibility checks go into the real-key test. The Right/Left row of the key table above must be updated by #42. - **#43 (Repo health)** changes sort order and adds search tokens. The seeded repositories in the test are two; if their order changes, the test's expected cursor keys change. Keep expectations on stable row keys, not positions where possible.

## Alternatives rejected

- **Run the real Omarchy shell code in CI** (clone or pin `omarchy`). Owner chose stubs. A pin is a new supply-chain dependency and a moving target; the real tree is large.
- **Call `panel.move()` and friends as today.** It skips `Keys.onPressed` (`:234-255`) and the focus handover, which are the very things that break. Rejected by decision 2.
- **Put the graphical test inside `nix flake check`.** Slows every `flake check`, and needs a compositor in the sandbox. Rejected by decision 3.
- **`cage` as the compositor.** Cage is a kiosk compositor and I did not find it supports `wlr-layer-shell` clients; the panel is a layer-shell surface. Not verified by running it. `weston` does not support layer-shell either.
- **`labwc`.** Works in principle (layer-shell and virtual keyboard) but sway is the more common headless test target and is simpler to start with `WLR_BACKENDS=headless`. Easy to swap if sway fails.
- **`ydotool` or `xdotool` for keys.** `ydotool` needs `/dev/uinput`, which hosted runners do not give and which could send keys to a real session when run locally. `xdotool` is X11 only. `wtype` talks only to the compositor it connects to.
- **Stored screenshot comparison.** The owner did not choose it; it breaks on theme and font changes.
- **Pixel grab to find rows.** Fragile and slow. The `layout()` geometry covers the three agreed failures.
- **Keep the missing-directory check.** Dropped by decision 5.
- **Retry the CI job once.** Forbidden by decision 6 and #36.
- **Expose the panel `ListView` via a property alias instead of `layout()`.** A larger public surface for the same data. A function is smaller and read-only.
- **A new flake package or `apps` entry for the test tools.** A `devShell` is a one-line list and is also the local entry point.

## Risks

- **GitHub runner behaviour (ubuntu-latest).** Sway headless, `wtype` and Qt Wayland in a Nix shell are known to work on desktops. I could not run sway here, so nothing in this spec is proven on a CI runner. The first run of the new job is the real test. If sway will not start there, the fallback is `labwc`, then a plan revision. If it cannot be made stable, this task stops and goes back to the owner rather than being retried.
- **`import Quickshell.Hyprland` without Hyprland.** `open()` reads `Hyprland.focusedMonitor` (`ActionsPanel.qml:44`). Today's test runs on razer under Hyprland. Under sway the import should load and `focusedMonitor` should be null, which `open()` already handles. Unverified. If it errors, the stub root can provide a `Quickshell.Hyprland` shim or the panel guards it.
- **Key timing.** `wtype` can send a key before the surface has focus. The readiness stage (mapped surface with keyboard focus, then a probe key) and the sequence-numbered state lines address this. Fixed sleeps are not used. A wrong wait would show up as a flake, and no rerun is allowed, so the waits must be state-based. Whether sway reports the layer-shell keyboard focus in a form `swaymsg` can query is unverified; if it does not, the probe key alone is the readiness signal.
- **Stub drift.** The stubs can pass while real Omarchy changed an API. Accepted by the owner. Mitigation: manual check before a release, written in the README. The stub check does not prove the panel's colour bindings, only that the stubs load.
- **p620-only failures (#36).** They were not explained. This job runs only on GitHub runners, so it does not rely on that. If the failure shows up in the new job, it is a new bug to chase and not a reason to rerun.
- **New failure mode for pull requests.** The job is slower (a Nix shell plus a compositor) and can fail where `nix flake check` passes. It is a separate job so the old check keeps its meaning. Whether it is a required status check is a repository setting for the owner.
- **`layout()` in shipped code.** It is read-only and small, but it ships. Cost of an alternative (a test-only copy of the panel) is worse.
- **Supply chain.** No new action or flake input. `sway`, `wtype` and `quickshell` come from the nixpkgs input already pinned in `flake.lock`, but they are additional packages the CI job fetches from the Nix cache. The CI job runs with `contents: read` only and no GitHub token.
- **Local runs on a real session.** The script starts its own sway in a private runtime directory and builds the child environment from scratch (see "Session bootstrap"). A bug there could send keys to the owner's desktop. The test refuses to run if the socket it waits for is not inside its own private directory.

Not verified: that sway headless, `wtype` and the layer-shell exclusive focus work on `ubuntu-latest`; that `Quickshell.Hyprland` loads without Hyprland; that `cage` lacks layer-shell; that `swaymsg` can report layer-shell keyboard focus; the exact package versions at the locked pin. Omarchy's terminal launcher (`omarchy-cmd-terminal-cwd`, `omarchy-default-terminal`) is not needed here; that is #44.

Proof the test can fail (run once each by the implementer, results recorded in `plan/`, no reruns to get a pass):

- Change one key in `Keys.onPressed` (for example `Qt.Key_Slash`, `ActionsPanel.qml:247`) and see the run fail with a message naming that key.
- Set the list `height` to `0` (`ActionsPanel.qml:305`) and see the layout stage fail.
- Set `WlrLayershell.keyboardFocus` to `WlrKeyboardFocus.None` (`ActionsPanel.qml:214`) and see the run fail at the readiness stage. (Removing `keys.forceActiveFocus()` from `open()` is not used: `keys` already has `focus: true` at `ActionsPanel.qml:233`, so that edit may not break the first key.)
- Make a row's height overlap its neighbour in the delegate and see the overlap check fail.
- Make a delegate zero-width or zero-height and see the selected-row check fail.
- Change `Polling.manual` so `r` queues no `summary` request, or `R` no `catalogue` request, and see the refresh stage fail.
- Remove `requestProc.running = false` from `close()` (`ActionsPanel.qml:57`) and see the close-during-request scenario fail.
- Run the failure scenarios with and without `python3` on `PATH`.

New tests added: key table above, layout check, helper-cannot-start scenario, close-during-request scenario, and the stub-loading check. Updated: `flake.nix` (invalid-directory block removed, `devShells.default` added), `.github/workflows/check.yml` (new `qml-smoke` job), `README.md` (CI statements). Confirm with `nix flake check` that p620 still passes with no desktop.
