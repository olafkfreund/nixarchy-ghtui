# Spec: Make the QML smoke test pass or fail deterministically

## Design

### 1. Hypothesis 1 from the source: refuted, pending one probe on razer

Hypothesis 1 said that `requestProc.onExited` can read `pageOutput.text`
before all of stdout has arrived. The source of the exact versions we ship
rules this out:

- **Qt 6.11.2** (`qtbase` linked by `quickshell-0.3.1`),
  `QProcessPrivate::_q_processDied()`: on Unix it calls
  `_q_canReadStandardOutput()` and `_q_canReadStandardError()` "so the data
  is made available before we announce death". Only then does it call
  `processFinished()`, which emits `finished`. `tryReadFromChannel` reads
  everything `FIONREAD` reports. A process that has exited has nothing
  left to write. If it wrote more than the 64 KiB pipe buffer, it could
  not have exited until Qt had read the rest.
- **Quickshell 0.3.1**, `src/io/process.cpp`, `Process::onFinished`: it
  calls `mStdoutParser->streamEnded(stdoutBuffer)` first, which sets
  `StdioCollector.text` (because `waitForEnd` is true by default) and emits
  `streamFinished`. Only after that does it emit `exited`. So
  `pageOutput.text` is already complete when `onExited` runs.

The one case that can still truncate is a grandchild that keeps stdout
open and writes after the direct child has exited. `actions.py` does not
do that: `request()` waits for `gh` with `communicate()`, and `main()`
prints the reply itself.

**Probe (one-off, on razer, not committed).** It confirms the source
reading at runtime. A scratch directory under `/tmp` holds a `shell.qml`
with one `Process` and one `StdioCollector`, both set up the same way as
`requestProc`. It runs each helper variant 200 times. In `onExited` it
compares `text.length` with the length the helper announced on stderr,
and prints one summary line per variant.

| Variant | Helper behaviour | Expected |
| --- | --- | --- |
| A | 1 MiB of JSON in 4 KiB `os.write` chunks, then `os._exit(0)` straight away | 200/200 complete |
| B | 200 KiB in one `sys.stdout.write`, then `flush()`, then `os._exit(0)` | 200/200 complete |
| C (positive control) | `print(...)` into a block-buffered stdout, then `os._exit(0)` without flushing | truncated or empty, which shows the probe can detect loss |
| D (known semantics) | a forked grandchild writes 0.3 s after the parent exits | truncated, which shows the only real hole |

Run it idle, then under 16 busy loops, as in the evidence run.

- **If A and B are complete and C and D are not,** Hypothesis 1 is
  refuted. Go on with sections 2–4.
- **If A or B lose data,** Hypothesis 1 is confirmed. Replace section 2
  with this fix in `ActionsPanel.qml`: handle the reply when both
  `requestProc.exited` and `pageOutput.streamFinished` have fired, keeping
  the exit code in a property. `onExited` alone is not enough. Also add
  the regression from section 2(c). Before the fix, variant A as the smoke
  test's fake helper must fail; after it, it must pass.

### 2. Smoke test: name the failure instead of timing out (`tests/qml-smoke.py`)

The p620 failures can't be reproduced (50/50 passed on razer), and their
status lines were lost. So a failure must say what happened on its first
run:

a. **Fail fast when polling stops.** In the 250 ms stage timer, before the
   stage branches:
   `if (panel.polling.auth) check(false, "polling stopped: " + panel.error)`.
   Any setup error (an empty or invalid reply, or `python3` failing to
   start) is a permanent stop in `Polling.complete`. Today that shows up
   as a vague timeout 17 s later. After this change it fails at once and
   names the error.
b. **Name the missing condition on timeout.** The 18 s message adds which
   stage-1 conditions are still false: `requests>=6`, jobs for
   `one/repo:7`, and `catalogueComplete`. It keeps `panel.status()`.
   Whatever triggers a timeout on p620 next time will be in that one line.
c. **Make every run exercise large chunked replies.** The fake `actions.py`
   adds a `"padding"` field of about 200 KiB to every reply. It writes the
   reply in 4 KiB chunks with `os.write(1, …)`, then calls `os._exit(0)`.
   `Polling.complete` ignores unknown fields. This costs about 3 lines, and
   it turns Hypothesis 1 into a check that runs every time rather than a
   one-off.

The 18 s and 25 s budgets stay as they are. The simulation in the intent
puts stage 1 at 5–7 s.

### 3. `test_cancellation_reaps_gh`: wait for readiness, not a clock (`tests/test_actions.py`)

Today the test polls for the pid file for at most 100 × 20 ms = 2 s. Under
load, two Python start-ups (`actions.py`, then the fake `gh`) can take
longer than that.

- The fake `gh` writes its pid to `pid.tmp` and then calls
  `os.replace(…, pid)`. That rename is the readiness signal, and the test
  never sees a half-written file.
- The test waits until the pid file exists **or** `actions.py` has exited.
  If `actions.py` exited first, it fails with "actions.py exited before
  starting gh". The only time limit is a 30 s hang guard. That matches the
  fake's `time.sleep(30)`, so it cannot fire while `gh` is alive and on
  its way to starting.
- The `SIGTERM`, `wait(timeout=3)` and `os.kill(child, 0)` assertions stay
  as they are. Reaping is `kill()` plus `wait()` in `request()`'s
  `finally`, and does not depend on start-up time.

### 4. Rerun allowance

No plan or review may allow a rerun of the smoke test or the unit tests.

`plan/2026-09-24-31-dead-code.md` on `main` still has the allowance: "A
single failure is therefore re-run, up to three runs in total. Two
failures in three runs count as a real failure." #31 is merged and done,
so that plan is a record, and its text and history stay as they are. As
part of #36's implementation, add one line right after that paragraph:
"Superseded by #36: no reruns."

If the smoke test fails, the failing line (section 2) goes on #36, or on a
new issue if #36 is closed.

## Alternatives rejected

- **Raise the 18 s timeout.** The intent rules it out, it hides stops, and
  the simulation says time is not the constraint.
- **Handle the reply on `streamFinished` instead of `exited` straight
  away.** The source shows that Quickshell already orders `streamFinished`
  before `exited`, so this changes nothing. It is kept only as the fix if
  the probe contradicts the source.
- **A FIFO or inherited pipe for `gh` readiness.** `request()` uses
  `Popen`'s default `close_fds=True`, so an inherited fd never reaches
  `gh`. A blocking FIFO open hangs forever if `gh` never starts, and fixing
  that needs `O_NONBLOCK` plus `select` subtleties. An atomic rename plus a
  liveness check is simpler and equally exact.
- **Run the smoke test in CI under a headless compositor.** It is out of
  scope (intent open question 2). It needs a new CI job and the Omarchy
  theme and shell paths, and it would not have caught a p620-only trigger.
- **Retry a failed helper reply inside `Polling.complete` rather than
  stopping.** That changes product behaviour decided in #24, where setup
  errors stop until a manual refresh. Nothing here shows the stop is
  wrong. The smoke test should report it, not route around it.

## Risks

- **Padding hides a real regression.** A 200 KiB reply is bigger than any
  real page of 100 runs at most. This is JSON-parse and IO cost in QML
  only, about 1 ms. If it ever slows stage 1 noticeably, drop it to 64 KiB,
  which still exceeds the pipe buffer.
- **The fail-fast check turns a slow run into a hard failure.** It fires
  only when `polling.auth` is true. That is a real stop, and the panel
  would show it to users as well.
- **The probe needs a display on razer.** It is a separate `quickshell -p`
  instance from `/tmp`. It needs no shell restart and does not touch the
  plugin directory. It is run under the agent-bus CLAIM/"done" protocol.
- **The p620-only trigger stays unexplained.** That is accepted. The next
  occurrence names itself (section 2), and #36 can be reopened with that
  line.
