# Spec: Text size keys make the panel's text bigger or smaller

## Design

### Scope

This is a presentation change. It touches `ActionsPanel.qml`, one pure function pair in `ActionsModel.js`, `keybindings.sh`, `README.md` and the tests. It adds no files, no storage, no settings and no GitHub requests. `Polling` does not change.

It lands after #42 (decision 6). Line numbers below are from `main` at 9882c84, checked in the current files. They are about five lines lower than the ones in the intent, which were taken from an older base. #42's plan moves several of them again, so the plan must re-find each spot by its quoted text.

### Owner decisions

These are binding. Each is restated with how the design meets it.

1. **Keys: Ctrl+= bigger, Ctrl+- smaller, Ctrl+0 reset to the theme size.** See "Keys".
2. **The keys work while typing in the search field. They never change the search text.** See "Keys". Ctrl keys are not typed into a search, and the search field's own handler takes them first.
3. **The size is remembered for as long as the shell runs. No file.** It is one `int` property on the panel root. The plugin stays loaded (`manifest.json:6`, `keepLoaded: true`), and `close()` (`ActionsPanel.qml:55-59`) only clears `opened`, so the property survives close and reopen. A shell restart resets it to the theme size.
4. **Range: 5 steps smaller and 5 bigger, 10% per step, relative to the theme size.** The step is an integer from -5 to +5. The factor is `(10 + step) / 10`: 50% to 150% of the theme size, in steps of 10 points (not compounding).
5. **The card keeps its size. More or fewer rows fit.** The card expression (`:224-225`) does not change.
6. **Order: after #42.**

### The size model

One property, three derived font sizes and one helper on the panel root (`ActionsPanel.qml`, near `:30`):

```qml
property int textStep: 0
readonly property int fTitle: Model.zoomed(Style.font.title, textStep)
readonly property int fBody: Model.zoomed(Style.font.body, textStep)
readonly property int fCaption: Model.zoomed(Style.font.caption, textStep)
function sp(n) { return Model.zoomed(Style.space(n), textStep) }
```

Two pure functions in `ActionsModel.js`, so `node` can test them:

```js
function clampStep(n) { return Math.max(-5, Math.min(5, Math.round(Number(n) || 0))) }
function zoomed(px, step) { return px > 0 ? Math.max(1, Math.round(px * (10 + clampStep(step)) / 10)) : 0 }
```

At step 0, `zoomed(px, 0)` is `px` for every integer `px`, because `px * 10 / 10` is exact. So the default is exactly the theme size. Everything stays relative to the theme: `Style.font.*` and `Style.space()` are read live, so a theme change, a `base-size` change or a monitor scale change still reaches the panel. There are no fixed pixel sizes.

**What scales (the text and the rows that hold it).** These are the sites on `main`:

Text that follows a font already needs no change: the search placeholder (`:301`, `font: searchField.font`) and the search height (`:273`, `font.pixelSize * 1.4`). The same holds for what #42 adds: its status line height is `searchField.font.pixelSize * 1.4`, and its text follows the fonts above.

Code that #42 to #46 add must go through the same helpers wherever it sizes text or a row. #46's `rowMin` (its three-row minimum list height) is the important one: if it stays on `Style.*` while the rows scale, the "three rows" guarantee is wrong at larger steps. The plan greps every remaining `Style.font` and `Style.space` in `ActionsPanel.qml` on the rebased tree and classifies each as text-sized (convert) or chrome (leave).

**What does not scale (the chrome).** The card size (`:224-225`), its padding (`:229`), the gaps between the header, search, list and footer (`Style.spacing.md` at `:262` and `:310`), the row's inner gap (`Style.spacing.sm`, `:326`), the hairline (`:306`), the border and the corner radius. They are the theme's frame, not text. Chrome that is made of text (header, search, status line, footer) still grows with its font, so it takes more of the fixed card at larger steps. That is the cost of decision 5.

**Why one ratio for text and rows.** A row holds text about 1.2 times the font size. The row minimums (`space(64)`, `space(40)`) are far above that at the default (a two-line row needs about 30 of 64). Scaling the font and the row by the same ratio keeps that margin at every step, so text is not cut vertically and rows do not overlap. Rounding differs by at most 1 px per value. The indent per level scales too, so tree levels stay distinguishable at 50% (9 px a level on the default theme) and at 150%.

**The two ends.** At 150% a two-line row is 96 units on a 12 px theme, so the 680-unit card shows about six of them after the chrome. At 50% the caption is 5 px (see Risks). Long names still elide (`:342`, `:352`, `:363`) and the list scrolls, as today.

### Keys

One function on the root returns `true` when it handled the event:

```qml
function textKey(event) {
    var m = event.modifiers
    if (!(m & Qt.ControlModifier) || (m & (Qt.AltModifier | Qt.MetaModifier))) return false
    if (event.key === Qt.Key_Equal || event.key === Qt.Key_Plus) setTextStep(textStep + 1)
    else if (event.key === Qt.Key_Minus) setTextStep(textStep - 1)
    else if (event.key === Qt.Key_0) setTextStep(0)
    else return false
    return true
}
function setTextStep(n) {
    textStep = Model.clampStep(n)
    list.forceLayout()
    list.positionViewAtIndex(cursor, ListView.Contain)
    showNotice("Text size " + (100 + 10 * textStep) + "%")
}
```

- **Two call sites, each as the first statement:**
  - The navigation handler, `keys` `Keys.onPressed` (`:239`): `if (root.textKey(event)) { event.accepted = true; return }`. It goes before `event.accepted = true` (`:240`) and, once #42 lands, before #42's modifier guard. That guard sets `accepted = false` for any Ctrl, Alt or Meta key, so it would swallow these keys if it ran first.
  - The search field handler (`:280`): the same line. Qt runs a `Keys.onPressed` handler before the item's own key handling, so the field never sees the key and cannot insert a character. The existing Enter, Esc and Up/Down handling in that handler relies on the same order. Decision 2 depends on it: some layouts may report a printable `text` for Ctrl+= (not verified), and only this order makes that harmless.
- **Match on `event.key`, not `event.text`.** With Ctrl held, `text` is often empty or a control character. #42 matches `?`, `g` and `G` on `text` because Shift decides their meaning. Here Shift must not matter, so `key` is right.
- **Shift is allowed.** On a US layout, Ctrl+Shift+= produces `Key_Plus`. Both `Key_Equal` and `Key_Plus` mean bigger. This covers Ctrl++ on layouts where `+` has its own key (for example German) or where `=` needs Shift. The decision names Ctrl+=. The `Key_Plus` alias is my addition (see Risks).
- **Alt or Meta with Ctrl is not taken.** Those combinations stay "left alone", as #42 says.
- **The keypad works.** Qt reports keypad `+`, `-` and `0` as the same keys, with `KeypadModifier` added.
- **Limits.** `clampStep` stops at -5 and +5. Pressing past the end changes nothing visible, so the notice shows "Text size 150%" and the user sees why. The notice uses #42's `showNotice()` and status line (3 seconds, fixed string). It also confirms Ctrl+0.
- **Selection and expansion are kept.** The key only changes `textStep`. It does not touch `entries`, `cursor`, `expanded` or `filterText`. `setTextStep` re-lays out the list and calls `positionViewAtIndex(cursor, ListView.Contain)`, the same call `move()` makes (`:98`), so the selected row stays in view.
- **No clash.** The existing keys are plain keys. #42, #43, #44, #45 and #46 add `y ? g G m v w i` and plain action keys. None uses Ctrl. Ctrl+R, Ctrl+O and Ctrl+J stay inert under #42's guard.

### Footer: the hint must not lose `Esc close`

The footer hint is one elided line (`:379-383`). At 150% a hint of about 90 characters needs about 1.5 times the width, and the tail, `Esc close`, would be cut. The footer gets `wrapMode: root.textStep > 0 ? Text.WordWrap : Text.NoWrap`. At step 0 and below it is the same line as today. Above it, the hint wraps and the list gives up the extra line (`:310` already subtracts `footer.height`). The hint text itself does not change (see "Docs").

## Alternatives rejected

- **Scale the whole card with `Item.scale` or a `Scale` transform.** It blurs text, does not change the layout, and the card would overflow the screen at 150%. It is not a theme-relative size.
- **Change `Style.fontBaseSize` or the font overrides.** `Style` is a shell-wide singleton. It would resize every Omarchy menu, which is what the intent says to avoid.
- **Plain `+`, `-` and `0`.** They are valid search characters, so they could not work in the search field (decision 2).
- **Store the size in a file or `Settings`.** The owner chose "while the shell runs" (decision 3), and the plugin keeps no files.
- **A table of fixed pixel sizes.** It breaks theme-relative sizing. A ratio of the live theme sizes does not.
- **Grow the card with the text.** The owner chose a fixed card (decision 5).
- **A pixel floor (for example, no smaller than 8 px).** It would be a fixed pixel size. It is raised as an owner question in Risks instead.
- **Compounding steps (each press changes the current size by 10%).** Up then down would not return. Linear steps do, and Ctrl+0 is exact.
- **Keep the arithmetic inline in QML.** The smoke test does not run in `nix flake check`, so rounding and clamping would be untested in CI. Two pure functions in `ActionsModel.js` are tested by `node tests/model.cjs`, which CI runs.

## Risks

- **The smallest step may be too small to read.** Step -5 is 50%. On the default 12 px theme the caption is 5 px and the body 6 px. That is the range the owner set (decision 4), so I added no floor. If it is too small, the fix is a narrower range, for example -3, and it is one constant in `clampStep`. **Needs the owner.**
- **Additions beyond the decisions.** Each is small and can be dropped. **Needs the owner:**
  - the `Key_Plus` alias for Ctrl+Shift+=;
  - the "Text size N%" notice;
  - the footer wrapping above step 0.
- **How Ctrl+= arrives is not verified.** I could not send real key events in this session. I expect `Qt.Key_Equal` with `ControlModifier` on a US layout, and `Qt.Key_Plus` with Control and Shift where `+` needs Shift. On layouts where `0` needs Shift (for example French), Ctrl+0 may arrive as another key unless Shift is held, and Ctrl+Shift+0 gives `Key_0`, which this accepts. These are symbol-based shortcuts: matching `event.key` with Shift allowed follows the symbol the layout produces, not the physical key. The manual check lists the layouts to try. Only if a tested layout fails, add the `Qt.Key_*` that actually arrives, after confirming it is not a different shortcut's key. No alias is added blind.
- **Whether `TextInput` would insert a printable `text` for Ctrl+=.** Not verified. The design does not depend on it, because the field's `Keys.onPressed` runs first and accepts the event. The check "type `ab`, press Ctrl+=, the text is still `ab`" proves it.
- **Delegate heights after a step.** `setTextStep` calls `list.forceLayout()` then `positionViewAtIndex(cursor, ListView.Contain)`. `rebuild()` already uses this pair (`:82-83`, `:86-88`). Whether the delegate height bindings have updated at that point is not verified. If a row ends partly out of view, defer the position call with `Qt.callLater`.
- **The 1 Hz rebuild.** `onNowChanged: rebuild()` (`:42`) keeps scroll by item position (`:72-75`). A step change is not a structure change, so it should not clash. The smoke test below covers it.
- **The footer at larger steps.** The wrap is one expression. At the largest step on a narrow card it may need more than two lines. The list gives up the height, so nothing overlaps. Not verified visually.
- **#42's status line and search note at 150%.** The status line elides a long error (allowed by the intent: "long names may still be shortened"). #42's coverage note ("recent runs loaded for N of M repositories") sits in the search row and could crowd typing space at 150% on a narrow card. #42 sets `searchField.rightPadding` from the note's width, so the field stays usable but shows less text. Not verified.
- **Behaviour change.** Ctrl+= and Ctrl+- now act. Today they reach nothing. Documented in the keys sheet and the README.
- **Order drift.** #43 to #46 add text and may land before or after this. The plan's grep (see "What scales") makes the check mechanical, but it must be re-run on the rebased tree.

## Owner answers (2026-11-16, spec approval)

These override any text above they contradict.

- **Range: -3 to +5, so 70% to 150% of the theme size.** The smallest step was 50%, which gives a 5 px caption on a 12 px theme. `clampStep` clamps to -3 and +5, and every "50%" in this spec (key table, `keybindings.sh` line, README, tests) reads "70%". A test asserts that step -4 clamps to -3. Decision 4 keeps 10% a step and 5 steps up.
- **Kept as specified:** the `Key_Plus` alias (Ctrl+Shift+= also makes text bigger), the "Text size N%" notice through #42's `showNotice()`, and the footer wrap above step 0.
