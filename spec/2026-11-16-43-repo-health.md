# Spec: Repo rows show their last result, and failing repos come first

## Design

### Scope and the owner's decisions

The owner approved these answers to the intent's open questions. They are binding, and each is restated as a decision with where it lands.

| # | Decision | Where it lands |
| --- | --- | --- |
| 1 | Every repository gets a last result from the same per-repo request, made without the `in_progress` filter. Cost stays the same. | `actions.py` `page_endpoint` (line 77), `Polling.js` `activity()` (line 149) |
| 2 | Only the latest result counts. No "recent failure" memory. | `r.last` holds one run |
| 3 | The last result is for the default branch only. | catalogue gains `default_branch`; `Polling.js` picks the run |
| 4 | Failed means `failure`, `timed_out` or `startup_failure`. | the same list as `icon()` (`ActionsModel.js` line 19) |
| 5 | The idle check interval stays 10 minutes. | `TIMING.idle` is unchanged |
| 6 | Keep 10 recent runs, plus a "load more" key. | PR (b), key `m` |
| 7 | Sort failing, then running, then the rest. No labelled sections. | `rows()` (`ActionsModel.js` line 38) |
| 8 | Search tokens are `branch:`, `actor:` and `is:failed`. | PR (b), `rows()` |
| 9 | Two PRs: (a) last result and sort, (b) search tokens and load more. | see Verification |

No new files, settings, dependencies or timers. The helper is still started with an argument array, still pins `github.com` (`request()`, `actions.py` line 47), and still only does GET reads.

### PR (a): last result and sort

**The activity request drops its status filter.** Today `page_endpoint` turns an `activity` task into `?status=in_progress&per_page=100&page=1` (lines 77 and 82). After the change it is `repos/<repo>/actions/runs?per_page=30`. It is still one request for each idle check, so the request count does not change (decision 1).

- A page of the newest 30 runs holds running runs, queued runs, and finished runs with their `conclusion`. That is everything the row needs.
- `read_page` stops returning `total` for `activity`. The unfiltered `total_count` counts every run in the repository, so it no longer means "running". The summary status pages (`status=in_progress` and the other unfinished states) keep their `total`, so #30's "+N more" row is unchanged. The condition at `actions.py` line 197 becomes `task.get("status") in ACTIVE`.
- `activity()` is called with `total` undefined for these pages, so `r.active` is the count of `in_progress` runs on the page (`Polling.js` line 163). The summary's own `in_progress` phase still passes `total`, so a busy repository still reports the true running count there. `r.hidden.in_progress` is only written from the summary path.
- **A full page is partial.** Today `partial` is `total > items.length` (line 151), which is false when `total` is undefined. That would turn every unfinished run that fell off a busy page into a "run" lookup (`awaitingFinal`, lines 153-158), an unbudgeted request. So `partial` also becomes true when `total` is undefined and the page holds 30 runs (a full page). The existing partial rule then applies: a missing unfinished run that is not `kept()` is dropped from the cache and costs no lookup. A page with fewer than 30 runs holds the whole history, so a missing run is looked up as today.
- **Every unfinished status is reconciled, not only `in_progress`.** The loop at line 154 handles only `in_progress`, and `recent()` keeps every unfinished run (line 144). On an unfiltered page, a `queued` or `waiting` run that later falls off the newest 30 would stay in `r.runs` for ever. The loop therefore treats any `status !== "completed"` run missing from the page the same way.
- **Trimming must not crash `activity()`.** `mergeRuns` trims completed runs to 10 (line 139), and line 162 then does `delete cached.awaitingFinal` on `runFor(...)` for every incoming run. With a 30-run page of completed runs, `runFor` returns `undefined` for the trimmed ones and the loop throws `TypeError`. That cannot happen today because only unfinished runs come back. The cleanup loop must skip runs that are no longer cached, and PR (a) adds this exact case (30 completed runs in one activity page) to `tests/polling.cjs`.
- A run that was running last check and has finished now usually shows up on the page as `completed`, so it needs no lookup. This is a saving only when the page holds it.

**The catalogue carries `default_branch`.** `read_page` builds each repository from `full_name`, `description`, `archived` and `disabled` (`actions.py` lines 177-178). Add `"default_branch": plain(row.get("default_branch") or "")`. `plain()` is the #32 filter, because a branch name is GitHub text. `Object.assign(existing, repo)` (`Polling.js` line 217) copies it onto the repository.

**One new field, `actor_login`, is added for run rows in PR (b), not here.** See below.

**`r.last` is the latest default-branch result.** In `Polling.js`, a small function `lastResult(r, runs, now, full)` is called from `activity()`, from the end of the summary snapshot (over `t.all`, line 236), and from the single-run lookup in `complete()` (`t.kind==="run"`, line 203, over `[resolved]`). Without that third call, a default-branch run that fell out of the newest 30, finished and was then looked up (or rerun, #45) would never update the row:

1. Keep runs where `status === "completed"` and `head_branch === r.default_branch`.
2. Take the one with the highest `id`. That is the same order `recent()` uses (line 143), so "latest" means one thing in the panel. A rerun keeps its id and its `run_attempt` changes, so a rerun of the newest run is seen. A rerun of an older run is not the latest.
3. Store `r.last = {id, conclusion, at: run.updated_at, url: run.html_url, branch: r.default_branch, confirmedAt: now}`. If no run qualifies, leave the previous `r.last` alone, except for `confirmedAt` (rule 5).
4. A higher id always replaces a lower one. An older id never replaces a newer one, so a stale page cannot move the result backwards. The same id replaces itself when its `updated_at` is not older, so a rerun that changes the conclusion of the newest run is seen.
5. **`confirmedAt` is the clock for "stale", not `r.activityAt`.** `activityAt` advances on every successful page (line 165), even when the page says nothing about the default branch. A page confirms `r.last` only when it holds a qualifying run, or when it reaches back past it (its lowest id is `<= r.last.id`, or the page is not full), because then any newer default-branch run would be on the page. Only a confirming page sets `confirmedAt = now`. Without this, a cached green result followed by 30 feature-branch runs would look freshly checked for ever.
6. **A changed default branch drops the cache.** If `r.last.branch !== r.default_branch` (the catalogue refresh at line 217 can change it), `r.last` is cleared before the rules above run, so a result from the old branch is never shown for the new one.

`cancelled`, `skipped`, `neutral` and `success` are not failures (decision 4). If the latest default-branch run was cancelled, the row says "cancelled" in the neutral colour and the repository is not failing.

**`recent()` keeps the last-result run.** `recent()` keeps 10 completed runs by id (line 144). On a busy repository, pull-request runs can push the default-branch run out. `kept()` (line 146) also returns true for `run.id === r.last.id`. This costs one extra row, and it means a failing repository always shows the failing run when you open it. This also means `kept()` is the one place that decides what is never dropped, as #30 left it.

**The row shows the result and its age.** `rows()` (`ActionsModel.js` lines 46-49) builds `info` and `status`. The new rule, in order:

| Repository state | `status` | `info` |
| --- | --- | --- |
| archived / disabled | `neutral` | `archived` / `disabled` (unchanged) |
| `repo.error` | `error` | `unavailable` (unchanged) |
| never checked | `neutral` | `not checked` (unchanged) |
| last result is a failure | `failure` | `✕ 3h · 2 running` |
| last result is success, checked recently | `success` | `✓ 3h · 0 running` |
| last result is success, check is old | `neutral` | `✓ 3h · 0 running · stale` |
| other result (cancelled, skipped) | `neutral` | `⊘ 3h · 0 running` |
| checked, no default-branch run held | `neutral` | `no result · 0 running` |

- **"Checked recently"** means `now - r.last.confirmedAt` is under three idle intervals, 30 minutes (`3 * TIMING.idle`). A cooldown or a slow scan can delay a check, and a page that does not confirm the result does not count (rule 5). The "no result" row uses `r.activityAt`, since there is no result to confirm. Past that, a green result is shown as stale and in the neutral colour, so it is never shown as healthy when we do not know. A failure stays red when stale, with the same "stale" suffix, because hiding bad news is worse than showing old bad news.
- **The age** is `r.last.at` against `now`, formatted with the same seconds/minutes/hours rule as `duration()` (lines 31-32), in a small `ago()` helper next to it. It reads "3h", not "3h ago", to keep the right-hand column short. The column is capped at 35% of the list width (`ActionsPanel.qml` line 352) and elides, and the card shrinks with the window (line 219), so there is no fixed minimum. The state and age come first in the text so an elided tail loses the running count or "stale" before it loses the result. The smoke test (`tests/qml-smoke.py`, which has no width or elision check today) sets a 640 px window and asserts the info text of the longest case, `✕ 3h · 12 running · stale`, is not truncated. If it is, that goes back to the owner as a design question (widen the cap or shorten the text), not a silent change.
- **A running repository that is also failing** shows `status: failure` (the red icon) with "2 running" in the text. Failing wins the icon and the colour. The running count is still readable.
- `statusColor` (`ActionsPanel.qml` line 166) already maps `failure` to `Color.urgent` and `success` to `Color.accent`. `Model.icon()` already has ✕ and ✓. The delegate (lines 321-326, 348-358) is unchanged. No new theme colour is added, and if the theme has no success colour the icon and the word still say it.

**The sort.** `rows()` replaces `b.active - a.active` with a rank:

1. failing (`status === "failure"`),
2. running (`active > 0`),
3. everything else, including archived, disabled, unavailable and not checked.

Within a rank, running repositories keep today's "most running first" order. Failing and "rest" repositories keep catalogue (pushed-at) order, which `Polling.complete` already preserves on each catalogue refresh (line 226). Nothing in a group is sorted by time, so a row does not jump when its age changes. The cursor follows the row by key (`selection()`, line 87), as it does today. There are no labelled sections and no new keys (decision 7).

**Search placeholder.** The idle text (`ActionsPanel.qml` line 293) says "running first". It becomes "failing, then running first".

### PR (b): search tokens and load more

**Search tokens (decision 8).** `rows()` splits the filter on whitespace. A word of the form `branch:<x>`, `actor:<x>` or `is:failed`, with a non-empty value, is a token. Everything else is plain text, matched exactly as today (repository name and description, and run name, title, branch and state, lines 39-41). An unknown prefix (`is:open`, `foo:bar`) and an empty value (`branch:`) are plain text. Tokens are case-insensitive.

- **`branch:<x>`** matches runs whose `head_branch` contains `<x>`. It is a substring, like the existing text search, so `branch:feat` finds `feature/x`.
- **`actor:<x>`** matches runs whose `actor_login` contains `<x>`.
- **`is:failed`** matches runs whose conclusion is in the failed list (decision 4).
- **Combination.** All tokens and the plain text must match (AND). A repository shows if at least one of its held runs matches every token, or, with no tokens, as today. When tokens are present the repository-name match no longer lifts the run filter, because "repository matches" says nothing about its branch or actor. Plain text in the same query still has to match the repository or the run.
- **No new requests.** Filters only apply to runs the panel already holds (the same rule as #30's "visible runs only"). A repository that has not been checked cannot match a token. This is a stated limit, not a bug.
- **Expansion survives filtering.** #42 changes this too. Nothing here depends on it.

**`actor_login` is added by the helper.** GitHub's run object has `actor` (an object with `login`). The helper only cleans `RUN_TEXT` (`actions.py` line 42) and passes the rest through (line 195), so a raw `actor.login` is untrusted text that bypasses #32. One small function sets `row["actor_login"] = plain(row["actor"]["login"])` when `actor` is an object with a string `login`, else `""`. It is called for the run-list rows (line 192) and for the single-run reply (line 179-ish, the `kind == "run"` branch), because `union()` (`Polling.js` line 121) can replace a cached list row with the looked-up run, which would otherwise lose `actor_login`. The panel searches and shows only `actor_login`, never `actor`. (`triggering_actor` is not used.) Event is not a token (decision 8), so `event` is not added.

**Load more (decision 6).** The selected repository keeps 10 completed runs today. A new key, `m`, raises that for the selected repository by 30, up to 100.

- `r.recentLimit` (default 10) replaces the literal 10 in `recent()`. The `recent` summary phase also asks for `per_page=<limit>`, so a later full summary does not shrink what `m` loaded.
- `page_endpoint` accepts an optional `limit` for `recent`. It must be an `int` from 1 to 100, else `ValueError("Invalid page limit")`. The default stays 10. It is built into the endpoint string from the validated integer, never concatenated from text.
- `m` creates one task of a new kind `more`, key `more:<repo>:`, group `interactive`, which fetches only the `recent` page. A `summary` task cannot be reused: its completion compares against the global `phases.length` (line 234), replaces the run snapshot, overwrites `hidden` and sets `summaryAt`, and it shares the key `summary:<repo>:`, so `ensure()` (line 19) would return an in-flight snapshot instead of a new task. The `more` completion only calls `mergeRuns` (union by id, then `recent()`), so it touches no `hidden`, `summaryAt` or unfinished runs. It costs 1 request, not the 6 of a full snapshot. `page_endpoint` and the helper's kind check (`actions.py` line 60) accept `more` and map it to `recent`.
- **Repeated `m`.** While a `more` task exists for the repository, `m` does nothing. The limit is raised (by 30, capped at 100) only when the task is created. A `more` reply that arrives after a full summary, or the reverse, is harmless because both only union runs by id. A reply for an old session is still rejected by the existing `requestId` and `generation` checks.
- **The panel says how many.** The repository's expanded rows show one line after the last run, using the existing `more` row kind: `last 10 runs fetched · m loads 30 more`. The recent page is unfiltered, so the fetched count is not the same as the completed runs held (a full page can be mostly unfinished runs), and the text says "fetched", not "shown". It appears only when the last recent fetch came back full (returned count equals the limit), because otherwise there is nothing more. The count is stored as `r.recentFetched`. At 100 it reads `last 100 runs fetched`. The `more` row today comes from unfinished runs (`ActionsModel.js` lines 52-57). The two parts are joined with " · " in the same row so a repository never has two "more" rows.
- `m` is free: the panel uses `j k h l r R o /` and Esc (`ActionsPanel.qml` lines 234-251), and #42 adds `y ? g G`.
- It is added to `keybindings.sh` and the README key table. The README search paragraph (line 123) and help text list the three tokens.

### Request cost

The intent asks for requests per hour, before and after.

| Item | Before | After |
| --- | --- | --- |
| Idle repository (check every 600 s) | 6 /h | 6 /h |
| Repository with a running workflow (15 s) | 240 /h | 240 /h |
| Selected repository (10 s activity, 60 s summary of 6 requests) | up to 360 + 360 /h | unchanged |
| First scan of N repositories | N | N |
| `m` (user action) | n/a | 1 each |
| Extra lookup for an unfinished run missing from the page | 1 each | 1 each only when the page is not full, else 0 |

For N repositories with none running: `6 N` requests an hour before and after. For 137 repositories that is 822 an hour, and the existing window limit (60 a minute, 1 s gap, `Polling.js` line 3) is unchanged. What does change is size. A run object is large. Measured on 2026-11-16 against `NixOS/nixpkgs` with `gh api`: `per_page=30` returned 422 KB and `per_page=100` returned 1.41 MB. Today an idle repository returns almost nothing, because only running runs come back. A typical small repository has far fewer and smaller runs, but I did not measure a typical repository, so that is unverified. This is why the page is 30 and not 100: 30 is enough to hold a default-branch run on most repositories, and 100 would be about three times the bandwidth. GitHub counts requests, not bytes, against the primary limit.

### Checks against GitHub

Run on 2026-11-16 with `gh api --hostname github.com` against `NixOS/nixpkgs` and the authenticated account:

- **Run fields exist.** A run has `conclusion` (null while running), `head_branch`, `event`, `actor`, `status`, `updated_at`, `html_url`, `run_attempt`. `conclusion` was `null` for 21 of 100 runs, `skipped` for 37, `success` for 41, `failure` for 1.
- **`default_branch` is in `GET /user/repos`.** `user/repos?per_page=1` returned `main` for the first repository.
- **The `branch` and `status` filters work together** (`?branch=master&status=completed` returned runs on `master`). I did not use them: see "Alternatives rejected".
- **Not verified:** the run size for a typical small repository, `total_count` behaviour on an unfiltered page past 1,000 runs (not used), and whether `updated_at` can move on a run that has already finished and is not rerun. The design depends only on the id for "latest" and uses `updated_at` for the age text.

## Alternatives rejected

- **`branch=<default>` on the activity request.** Smaller payload and exact default-branch results. But it hides running workflows on every other branch and on pull requests, so "N running" would stop meaning "running". It would also need `default_branch` before the first check. The owner chose the unfiltered request.
- **A second request for the result** (activity plus a `status=completed&per_page=1&branch=…`). This doubles the idle cost, which the intent forbids and the owner ruled out.
- **Fetching results only for repositories the user watches.** Needs a watch list and a setting, and unwatched repositories would be silently "unknown". The owner chose every repository.
- **Remembering recent failures** (a failure followed by a pass stays visible for a while). More state and more history to hold. The owner chose latest only.
- **Last result across all branches.** A failed pull-request run on a feature branch would make a repository "failing". The owner chose default branch only.
- **Counting `cancelled` as failed.** Cancelled runs are usually manual or superseded. The model already draws them neutral (`ActionsModel.js` line 21).
- **Labelled sections** ("Failing", "Running", "Healthy"). More rows and a rule for empty sections, and the cursor and `selection()` logic would need to skip headers. The owner chose a plain order.
- **Sorting by failure time.** Rows would move every refresh. Catalogue order inside a group is stable.
- **Checking idle repositories more often.** It would multiply the cost. The owner kept 10 minutes. Short runs can still be missed: see Risks.
- **Letting `m` start a full summary.** 6 requests to fetch 1 more page. A one-phase task is 1.
- **A regex or query language for search** (`-branch:`, `OR`, quotes). More surface than three tokens need. Plain text still works.
- **Showing `actor.login` unfiltered.** Bypasses #32, because the helper passes unlisted fields through.

## Risks

- **Bandwidth.** The activity page is much larger than an in-progress-only page. On a slow link or a busy repository an idle pass reads megabytes more. It is capped at 30 runs. If it hurts, the fix is a smaller `per_page`, which is one number, at the cost of missing the default-branch run on busy repositories.
- **Busy repositories can show "no result".** If the newest 30 runs are all pull-request runs, there is no default-branch run on the page, and the row says "no result" until one appears. It is never shown as healthy. The selected repository's summary (10 recent runs, more with `m`) can find an older one.
- **A short run can still be missed.** The interval is 10 minutes (decision 5). A run that starts and ends between two checks is seen on the next check, because its conclusion is on the page, so this is better than today for the result. The running count can still miss it.
- **A cooldown delays results.** The row says "stale" after 30 minutes, not "unknown". Until then it shows the last known value. The user is promised "at most 30 minutes old, or marked stale".
- **A failure on a run that then fails to load.** If a repository has `error` set, it is "unavailable" and ranked in the rest, even if the last known result was red. That matches today's behaviour for errors.
- **`active` semantics.** `r.active` for an idle repository is now the count of `in_progress` in the newest 30. A running workflow older than the newest 30 runs falls off a full page and is dropped from the cache with no lookup (the full-page rule above), so a long run on a busy repository is no longer counted as running. The selected repository is not affected, because its summary uses the filtered `in_progress` phase.
- **Decision 1 has a limit.** A bounded unfiltered page cannot guarantee a default-branch result for every repository: if the newest 30 runs are all on other branches, the row says "no result", or keeps an old result that is marked stale once it is not confirmed (rule 5). This follows from the owner's choice of one unfiltered request and is not fixed here.
- **`r.last` and the 137-repository test.** The existing simulation returns empty idle pages (`tests/polling.cjs` line 35), so "same request count" is proved there only for empty pages. PR (a) adds a busy-page fixture (full pages of mixed runs, some unfinished and missing) and asserts the request count against the old behaviour.
- **Overlap with #30.** `hidden.in_progress` is now written only by summary. The "+N more in_progress" count for a non-selected repository can be out of date by up to the summary age. #30's tests must be updated, not weakened.
- **Merge order and the other issues:**
  - **#41 (polling).** Touches `Polling.js` `complete()` and `seed()`, and slows background polling as quota falls. That is compatible: slower checks make results "stale" sooner, which the row says. #41 also clears repos on an account switch, so `r.last` goes with them. It drops cached job details for runs no longer listed, and `kept()` must still protect `r.last.id`. #41 lands first. Rebase this work on it and re-run `tests/polling.cjs`.
  - **#42 (panel UI).** Lands after #41 and before this. It changes the status line, the run row text, and keys (`y`, `?`, `g`, `G`). It also adds an "N repositories have run data loaded" count in the search area. The placeholder text edited here is the same text. Use #42's version and add the "failing" words to it. `m` does not collide. The accessibility properties #42 adds must cover the new repo-row text.
  - **#44-#47.** #45 (rerun) can change a run's conclusion. The refresh it triggers goes through `activity()` or the run lookup, so `r.last` follows. #46's detail pane can read `r.last`. #47's smoke test stubs `qs.Commons` and `qs.Ui` and drives real keys, and needs the fake helper to return a failing repository. No dependency on #44.
- **QML and the field list.** `shownFields` (`ActionsModel.js` line 93) lists the row fields `syncRows` compares. The repo row still only uses `title`, `subtitle`, `status`, `info`, so it needs no change. If a plan step adds a field, update that list.
- **Tests that assume the old request.** `tests/test_actions.py` lines 162-165 assert the activity page and its `total`. They change in PR (a). The same applies to `tests/polling.cjs` fixtures for activity.
