# Spec: Run actions from the panel

## Design

### Scope and owner decisions

The panel gets its first write path: rerun all jobs, rerun failed jobs, and cancel, on a selected run. Nothing else writes. Dispatch, approving deployments, force-cancel and debug-logging reruns are out.

Owner decisions on the intent's open questions (binding):

1. First change is rerun failed, rerun all and cancel. `workflow_dispatch` comes later and is done from a terminal. Question 2 does not apply.
3. One confirmation for every action: the same y/n. No typed repository name.
4. Approving deployments is out of scope.
5. One key per action. No action menu.
6. Always available. There is no setting to turn writes off.
7. Writes do not count toward the polling budget (`TIMING.perWindow`), but they respect a GitHub cooldown.
8. The result goes on the status line. The affected run is refetched at once, subject to the cooldown.
9. A read-only token fails the action with an error that names the missing permission. The plugin does not probe first.

### Keys

| Key | Action | Offered when the selected row is |
| --- | --- | --- |
| `a` | Rerun all jobs ("again") | a run with `status === "completed"` |
| `f` | Rerun failed jobs | a run with `status === "completed"` and conclusion `failure`, `timed_out`, `startup_failure` or `cancelled` |
| `c` | Cancel | a run with `status !== "completed"` |

These are free today (taken: `r R o / j k h l`, `ActionsPanel.qml` lines 234-253). `a`, `f` and `c` are not offered on repo, job, step, "more" or message rows. Jobs and steps carry a `run` field, so acting from them would be cheap later. Acting on the whole run from a job row is easy to misread, so the first change keeps it to run rows.

The status and conclusion are read from the raw run, not from the row. A row (`rows()`, `ActionsModel.js` line 63) carries `run` as an ID string and `status` already mapped through `state()` (a failed run shows `failure`, not `completed`), and it has no conclusion, run number or branch field. So pressing a key resolves the raw run with the existing `Polling.runFor(s, row.repo, row.run)` and passes that to `actionsFor()` and `describe()`. If the raw run is gone, the key does nothing.

A key that is not offered does nothing and puts the reason on the status line ("Only a finished run can be rerun"). It never opens a confirmation.

Coordination: #42 adds `y`, `?`, `g`, `G`. #44 adds log and watch keys. #43 adds a load-more key. None of them may take `a`, `f` or `c`. While a confirmation is open, the confirmation handler runs first, so `y` means "confirm" there and "copy link" (#42) everywhere else.

### Helper: a closed write list in `actions.py`

`actions.py` gets a second mode, `act`, next to `page` (`main()` accepts only `page` today, line 213). It takes one JSON argument: `{"action": "rerun" | "rerun-failed" | "cancel", "repo": "o/r", "run": "123", "requestId": n}`.

The action maps to a fixed path, never to text from the task:

| Action | Request |
| --- | --- |
| `rerun` | `POST repos/{repo}/actions/runs/{run}/rerun` |
| `rerun-failed` | `POST repos/{repo}/actions/runs/{run}/rerun-failed-jobs` |
| `cancel` | `POST repos/{repo}/actions/runs/{run}/cancel` |

- `request()` (line 45) gets a `method` parameter. It adds `--method POST` and nothing else. No `-f`, `-F` or `--input`, so there is no body and no `@file` reading. The argument list is still `["gh", "api", "--hostname", "github.com", "--include", "--method", "POST", endpoint]`. Host pinning is unchanged.
- A new `write_endpoint(task)` does what `page_endpoint` does: `repo_name()` (line 19), a run-ID check (the one at lines 70-72, moved into a small shared helper), a positive int `requestId`, and a closed action table. Anything else raises `ValueError("Invalid action")`.
- The module docstring (line 1) changes from "Read-only GitHub Actions data" to "GitHub Actions data and a closed set of run actions". The helper still cannot send an arbitrary request.
- `write_action(task)` reuses `http_reply()` (line 85) and the rate-limit header parsing from `read_page()` (lines 126-160). To avoid copying it, lift that header block into one function that both call. Do not fork it.

Reply shape: `{requestId, action, httpStatus, ok, error, errorType, retryAt, remaining, resetAt, updated}`. `errorType` is one of:

| Condition | errorType | Message (fixed text, plus sanitised GitHub text where noted) |
| --- | --- | --- |
| 2xx (rerun 201, cancel 202) | none | none. The panel writes the success text. |
| 429, `remaining == 0`, `retry-after`, "rate limit" in the body (same test as line 162) | `rate` | "GitHub rate limit" |
| 401 or "auth login" on stderr | `auth` | "Authenticate with gh auth login" |
| 403 or 404 | `refused` | "Needs Actions write on {repo}: " + GitHub's message |
| 409, 422 and other 4xx | `refused` | "GitHub refused: " + GitHub's message |
| `gh` missing | `setup` | "Install gh (GitHub CLI)" |
| Timeout, `gh` exit with no HTTP reply, unreadable reply, 5xx | `unknown` | "Outcome unknown; check GitHub before retrying" |

A 403 or 404 can mean a missing permission, a run past the 30-day rerun window, or a repo the token cannot see. GitHub's own message is what separates them, so the message is passed on. It goes through `plain()` (line 27) and is cut to 120 characters. The permission hint is added for 403 and 404 only. A missing permission is the usual cause, and the hint matches decision 9.

The write mode never uses `permission` (the existing type). That keeps a refused write from sending the repository to `blocked` in `Polling.complete()` (lines 187-191).

`unknown` is deliberate for every case where GitHub's answer was not read. A killed or timed-out `gh` does not prove that nothing happened. The panel never retries an `unknown` action.

`main()` echoes `requestId` on error the same way `page` mode does (lines 213-243). The error type for a failure that happens before any request is built is `setup`, because nothing was sent. If `main()` fails after `gh` started, for example a crash with no output, the panel treats it as `unknown` (see below).

### Panel: `ActionsModel.js`

Small pure functions, so the logic is tested in Node and not only in QML:

- `actionsFor(run)` takes the raw run (from `Polling.runFor`) and returns the list of offered actions (`["rerun","rerun-failed"]` or `["cancel"]` or `[]`) from `status` and `conclusion`.
- `describe(action, repo, run)` takes the raw run and returns the confirmation and result text. The text is ordered so the part that must stay visible comes first and the descriptive part comes last, because the footer elides on the right (`ActionsPanel.qml` line 371) and `plain()` (`actions.py` line 27) strips control characters but does not limit length:
  - confirmation: "Rerun failed jobs? y yes · n no — owner/repo #42 CI (main)". For cancel: "Cancel run? y yes · n no · cannot be undone — owner/repo #42 CI (main)".
  - result: "Rerun of failed jobs requested: owner/repo #42 CI (main)".
  - `describe` cuts the workflow name and branch to 30 characters each, so only the tail can be elided at the smallest panel width.
- `actionReply(stdout, code, requestId)`: like `reply()` (lines 2-6) but for writes. Empty stdout with code 127 gives `setup` "python3 not found" (nothing was sent). Empty stdout with any other code gives `unknown`, not `setup`. `reply()` is left alone, because `setup` there means polling stops, which is wrong for a write.

### Panel: `ActionsPanel.qml`

State: `confirm` (null or a pinned target), `actionBusy`, `actionText`, `actionError` (bool), `actionId`.

- **Pinned target.** Pressing `a`, `f` or `c` on an eligible row stores `{action, repo, run, text}`. `repo` and `run` come from the row; `text` comes from `describe()` on the raw run found by `Polling.runFor`. It does not store a row key or index. Polling rebuilds and reorders rows (`rebuild()`, lines 68-92), but the confirmation holds strings, not a reference. Confirming sends exactly the repo and run that were named. This meets the intent's "cannot confirm a different target".
- **Modal keys.** While `confirm` is set, `Keys.onPressed` (line 234) handles it first and swallows everything: `y` confirms, `n` or Escape cancels, all other keys do nothing. Enter is not a confirm key, so a stray Return from the previous action cannot send it. Auto-repeat is ignored (`event.isAutoRepeat`), so a held `y` cannot fire twice. Escape backs out of the confirmation only. It does not clear the filter or close the panel. `close()` (line 54) clears `confirm`. The search field has its own handler (line 275); search editing cannot start while a confirmation is open, because `/` is swallowed too, and a confirmation cannot open while the search field has focus, because the action keys are only wired in the navigation handler.
- **Confirm line.** The confirmation text replaces the footer (line 371) and uses the order above, so the action, `y`/`n` and the repository stay visible when the end is elided. The footer is the only line that is always visible today. The search placeholder (lines 292-293) hides as soon as you type or focus the field.
- **Local gates, no request.**
  - `now < polling.cooldown`: the action is refused with "GitHub paused until HH:MM. Try again then." (reuses `cooldownText`, line 31). This is decision 7's "respect a cooldown".
  - `actionBusy`: refused with "An action is already running". One write at a time.
- **Separate process.** A second `Process { id: actionProc }` runs `["python3", helper, "act", JSON.stringify(task)]`. It does not use `requestProc`, `workerBusy` or `Polling.flight`:
  - `complete()` discards a reply after the panel closes or the generation changes (line 169). A write result must not be discarded.
  - `close()` kills `requestProc` (line 57). A write in flight is allowed to finish, and the helper's own 25 s limit still applies. If the shell itself goes away, the child dies and the outcome is `unknown`. This is the one case the panel cannot report.
  - It handles a failed start the way #24 does (a failed start emits only `running=false`, lines 201-202) with its own `actionStarted` flag. A failed start means nothing was sent, so it reports `setup` "python3 not found".
- **Reply handling.** The panel checks `requestId` (its own `actionId`) the way `receivePage()` does (lines 151-165). A reply with the wrong ID, or that does not parse, is `unknown`. Its text is logged with `console.warn`, but only fixed text is shown.
- **Result.** `actionText` is shown on the footer line for 10 seconds (a `Timer`) or until the next action key. A failure uses `Color.urgent`, as `error` does (line 294). Texts:
  - ok: "Rerun requested: …", "Rerun of failed jobs requested: …", "Cancel requested: …", followed by the repository, run number and name from `describe()`. "Requested", not "started", because GitHub only accepted the request (a cancel returns 202).
  - If a cooldown holds the refetch back, append " · refresh waits until HH:MM". This is the intent's "say so instead of stale state".
  - failures use the fixed texts in the table above.
- **Refresh after success.** `Polling.touch(s, repo, run, now)` (new) makes a run lookup due now and re-asks for the summary:
  - It gets or creates the task with `ensure(s, "run", repo, run, "interactive", now)` and then sets `t.due = now` explicitly. `ensure()` (`Polling.js` line 19) leaves an existing task's deadline alone, so a lookup that was backing off would otherwise stay delayed.
  - If that task is already in flight (`s.flight.key === t.key`), the reply being waited for may have been read before the write. The task is marked `t.again = true`, and `complete()` re-arms it (`due = now`, `again` cleared) instead of deleting it (line 211). The post-write lookup is then always a later request than the write.
  - It deletes `r.summaryAt` for the repo, so the next `next()` also seeds the selected repository's summary.
  - A rerun is seen by `invalidateJobs` through `run_attempt` (lines 125-130); the status flip is seen by the summary. Both are ordinary polling requests, so they count toward `perWindow`, wait for `gap`, and wait for `s.cooldown` in `next()` (line 98). "At once" means due now, subject to the cooldown, the gap and the fairness slots in `next()` (line 103). An interactive task wins 3 of 5 slots, but another group's due task can be sent first on the other two. This is accepted and is one request, not a delay of minutes.
- `status()` (line 60) adds `action` and `actionBusy`, so the smoke test can read them.

`ActionsPanel.qml` is the only file where the key and the confirmation are wired. `menu.py` and `manifest.json` do not change.

### Panel: `Polling.js`

- Lift the cooldown block of `complete()` (lines 176-181) into `cool(s, reply, now)`, and call it from `complete()` and a new `noteWrite(s, reply, now)`. A write reply with a retry deadline, `429`, or `remaining === 0` then extends `s.cooldown`, the same as a read. Writes spend GitHub's quota, so a write that used the last request must pause polling. `noteWrite` does nothing else: it does not touch `s.error`, `s.auth`, a repository's `blocked` or `error`, `tasks`, or `s.starts`. A refused write cannot hide a repository's activity.
- `touch()` and the `again` flag in `complete()` as above.
- `s.starts` is not changed by writes (decision 7).

### Facts checked

- `gh run rerun --help` (gh 2.104.0): `--failed`, `-j/--job`, `-d/--debug`. `gh run cancel --help`: `--force`. We do not call these commands. They are the reason the helper uses `gh api`.
- GitHub's REST description (`rest-api-description`, `api.github.com.json`): `POST .../actions/runs/{run_id}/rerun` and `.../rerun-failed-jobs` answer 201 and take an optional `enable_debug_logging` body field (default false). `POST .../cancel` answers 202 and 409, and takes no body. Classic tokens and OAuth tokens need `repo`.
- docs.github.com, "Cancel a workflow run": the fine-grained token needs "Actions" repository permissions (write). The same page type is used for rerun. I read the cancel page text and the REST description for rerun; I did not read the rerun page's permission table separately.
- `gh api --help`: `--method POST` with no `-f`/`-F`/`--input` sends no body. The default method is POST only when fields are given, so `--method POST` must be explicit.
- Against the code: `ensure()` keeps an existing task's `due` (`Polling.js` line 19); `complete()` deletes the finished task (line 211); `rows()` emits mapped `status` and no `conclusion` (`ActionsModel.js` line 63); the footer elides on the right (`ActionsPanel.qml` line 371).

Not verified (I did not send a write, since this would change a real repository):

- The exact JSON message GitHub returns for each refusal (rerun of a running run, a run older than a month, cancel of a completed run). The design passes the message through, so wrong guesses cannot make the text wrong.
- Whether GitHub flips the run to `queued` before the first refetch. Handled by seeding the summary; see Risks.
- The fine-grained 403 versus 404 split. Both are treated as "needs Actions write".
- The Omarchy launcher command. Not needed here; it is #44's.

## Alternatives rejected

- **`gh run rerun`, `gh run cancel`.** They fetch the run first and print prose on stderr. There is no HTTP status or rate-limit header to read, so we could not tell a refused write from an unknown one, and the text varies with gh versions. `gh api` returns what `http_reply()` already parses.
- **A generic `gh api` pass-through in the helper.** It would break the closed list and the "no arbitrary request" rule. The action name picks a fixed path.
- **Optimistic UI** (mark the run queued or cancelled before GitHub answers). Wrong if the write is refused or the outcome is unknown. The panel shows only what GitHub confirmed.
- **Sending writes through the polling worker** (`requestProc`, `Polling.flight`). It would share `workerBusy`, be killed by `close()`, and be discarded by `complete()`'s generation check. A write is not an idempotent read.
- **Counting writes in `s.starts`** (decision 7). Rejected by the owner. A user's rerun should not wait behind polling.
- **Marking the repo `blocked` on a 403 write.** The existing `permission` path does this for reads (`Polling.js` lines 187-191). For a write it would hide a repository because one rerun was refused. Writes use `refused`.
- **Auto-retry after `unknown`.** GitHub's rerun has no idempotency key. A retry after a timeout can start the run twice, and it costs runner minutes.
- **A typed repository name for cancel, or a stronger prompt** (decision 3). One y/n for all. The text for cancel adds "cannot be undone".
- **One key that opens an action list** (decision 5). It would need a menu control the panel does not have. Three keys are enough.
- **Shift-case keys** (`R`-style). Keys that differ only by case are easy to mistake; `r`/`R` already exist.
- **A setting to keep the panel read-only** (decision 6). The plugin keeps no state file. A read-only token is the way to stay read-only, and the README says so.
- **Probing the token before offering actions** (decision 9). It costs a request, and a fine-grained token's permissions are not readable from a header for classic scopes. The action fails with a named permission instead.
- **Offering actions on job and step rows.** Easy to add later, but "rerun" on a step reads as "rerun this step". Run rows only.
- **Force-cancel, `--debug` reruns, per-job rerun (`-j`).** Not asked for. Force-cancel is a separate, riskier endpoint.
- **Putting the result in the search placeholder** (lines 292-293). It is hidden when you type or focus the field, so a result could be missed.

## Risks

- **Real side effects.** A rerun spends billable runner time and can trigger deployments. A cancel is final. The confirmation names the repo, run and action, applies to that pinned run, and Enter and auto-repeat cannot confirm it. A run that changed state between the keypress and `y` is handled by GitHub, with 409 or 403 shown as "GitHub refused".
- **Long names.** A workflow name is not length-limited by the helper. `describe()` cuts name and branch to 30 characters and puts the action, `y`/`n` and the repository first, so eliding the tail cannot hide what is being authorised. This is checked at the smallest panel width (see Verification).
- **Stale eligibility.** Offered actions come from cached run data. GitHub is the authority; the cost of a stale gate is a refusal message, not a wrong action.
- **Double rerun on an unknown outcome.** A timeout (25 s) or a shell restart can leave the write done but unreported. The panel says "Outcome unknown; check GitHub before retrying" and never retries. The user can still press `a` again, which asks for confirmation again.
- **Cancel is asynchronous.** 202 means accepted. The run may stay `in_progress` for a while, so the panel shows "Cancel requested" and the next refetch shows the real state. Rerun is not offered until the run is `completed`.
- **Run status lag after rerun.** If the run still reads `completed` at the first refetch, the panel shows the old state until the summary (seeded now) or the next scheduled poll. This is stale, not wrong. If this proves common on a real run, add one more `touch` after `TIMING.followup`; do not add it now.
- **Refresh race.** A run lookup already in flight when the write finishes may have been read before the write. `touch()` marks it `again`, so a second lookup follows. Without this, the old reply would delete the task and nothing would refetch the run.
- **Token and org policy.** A fine-grained token without Actions write, an SSO-unauthorised token, or an org that forbids it gives 403 or 404. The message names the permission and shows GitHub's text. A run older than 30 days is refused by GitHub even with write access, with GitHub's own message.
- **Rate limit during a write.** The write respects the cooldown and feeds `noteWrite`, so the polling scheduler sees the same cooldown. A write that gets a secondary-limit 403 is classed `rate`, not `refused`, by the same test as reads (line 162).
- **Untrusted text.** GitHub's message and run names are shown. The helper passes them through `plain()`, caps the message, and the QML draws them as `Text.PlainText`. The confirmation text is built from fields already sanitised by the helper at fetch time. `repo` and `run` still go through `repo_name()` and the run-ID check before they reach `gh`.
- **Overlap with other in-flight issues.**
  - #41 rewrites parts of `complete()` (catalogue 403 stop, bad steps, quota slowdown). The `cool()` extraction and the `again` flag are small but touch the same lines, so land after #41 and rebase. #41's quota slowdown reads `reply.remaining`; passing write replies through `noteWrite` keeps that count honest. #41 item 3 (account switch on open) cannot leave a confirmation behind, because `close()` clears it. #41 item 5 (stale queued runs) shares the run refetch this change triggers.
  - #42 owns the always-visible status line and the keys sheet. Recommended order: #41, #42, then #45. Then the result and confirmation move from the footer to that line, and `?` lists the new keys. If #45 lands first it uses the footer, and #42 moves it. #42's accessibility properties (item 11) must cover the confirmation line.
  - #43 (last result and sort) changes `rows()` ordering and adds search tokens. It does not touch the keys here. `actionsFor()` reads the raw run, not the row position.
  - #44 (logs and watch) takes new keys: keep them off `a`, `f`, `c`. A rerun of a watched run creates a new attempt of the same run ID; #44 must say whether the watch follows it. This spec does not decide that.
  - #46 (detail pane, account display) is helped by this change: showing the active account tells the user whose token the write uses. It has no code overlap.
  - #47 (CI smoke test with real key events) takes over the automated key flow later. This change requires one documented real-keyboard check on a host (see Verification) and does not wait for #47.
- **Quickshell 0.3.1 process quirk.** A failed start emits only `running=false`. The second `Process` handles this the way #24 does. Only a host with Quickshell can prove it (see Verification).
- **Hosts.** The helper and the model run anywhere with python3 and node. The QML changes need a Quickshell + Omarchy host (the Razer, per #36).
