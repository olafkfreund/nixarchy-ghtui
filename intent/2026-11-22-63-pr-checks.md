# Intent: A pull-request checks view in the panel

## Problem

The panel shows workflow runs per repository and nothing about pull
requests. To see whether your pull request's checks pass, or what is still
running on one you were asked to review, you leave the panel for GitHub.
Issue #63 (split out of #46 by the owner on 2026-11-16) asks for "check
status for open pull requests of the listed repositories" and says it needs
its own intent because it adds a new kind of request and has to fit the
request budget.

What the code does today:

- **The helper's page reads are fixed REST endpoints** (`actions.py`
  `page_endpoint`, sent by `request()` through `gh api --hostname
  github.com`): the account (`user`), the catalogue (`user/repos`), and a
  repository's workflow runs, one run, and a run's jobs. Logs use a
  separate `gh run view` path. There is no pull-request, check-run,
  commit-status, search or GraphQL call.
- **Errors and quota are REST-shaped.** The helper classifies failures by
  HTTP status and a top-level `message`, and reads one
  `x-ratelimit-remaining`/`x-ratelimit-reset` pair, which `Polling.js`
  stores as a single `remaining`/`resetAt` and uses to slow background
  work 3× and 10× below 1,000 and 300.
- **A pull request's checks are not a list of Actions runs.** GitHub rolls
  them up per head commit from check runs (Actions jobs and other GitHub
  Apps) and commit statuses (older integrations). An Actions check run is a
  job, not a workflow run. Matching cached runs by commit would miss every
  non-Actions check; the cache keeps each repository's unfinished runs and
  10 completed ones by default (up to 100 with `m`).
- **Requests share one scheduler**: one request at a time, at most 60 a
  minute, one second apart, logs counting four; selected and inspected
  repositories take interactive slots while the panel is open. Only watched
  runs are polled while closed (#44).
- **Links are pinned to github.com.** `ActionsModel.js` `browsable()` lets
  `o` and `y` act only on `https://github.com/...` URLs.
- **The panel has one view** (`ActionsModel.js` `rows()`). The `p` key is
  free; there is no `q` key (Esc closes).
- **The sister plugin designed the same feature for GitLab** (nixarchy-gltui
  #40): a second view, switched with one key, listing your own open merge
  requests (authored only; review requests were left for later) with their
  head-pipeline status.

## Proposed outcome

When this is done, from the open panel and with the keyboard only:

- **One key switches** between the repositories view and a pull-request
  view, and back. The header says which view is shown. Switching back keeps
  what was expanded, filtered and selected in the repositories view.
  Reopening the panel shows the view it was closed in.
- **The view lists open pull requests** (which ones is open question 1),
  most recently updated first, up to a cap, never from archived
  repositories. When there are more, the last row says so. Each row shows
  the repository, `#N`, the title, the head branch, a draft mark and the
  overall result GitHub reports for the head commit (pass, fail, running,
  or none). The overall result comes from GitHub's rollup, not from the
  capped list of checks, so a failing check past the cap still makes the
  row fail.
- **A pull request expands to its checks**, each with its name and result
  (pass, fail, running, queued, skipped, cancelled, neutral or action
  required), whichever system reported it (open question 2). Past the
  check cap the last row says "more on GitHub".
- **The result is never guessed.** A row says the result; "no checks" only
  when GitHub answered and reported none; "checks unavailable" when GitHub
  withheld them (permissions, single sign-on, a partial reply); and how old
  the result is when older than its refresh target. A result belongs to
  the head commit it was read for, so after a force-push the old result is
  not shown as the new one's.
- **Links stay on github.com.** `o` and `y` act on the pull request, or on
  a check's GitHub page. A check whose only link is outside github.com
  (many commit statuses) is not opened; the footer says so and `o` on its
  pull request still works.
- **It stays current while you look, best effort.** The list refreshes on
  a bounded interval, faster while some shown pull request has running
  checks, and on `r`. While the pull-request view is shown, the
  repositories view's selected and inspected repositories stop taking
  interactive slots (background repository polling continues as today);
  switching back stops pull-request reads. A pull request that closes or
  leaves the list disappears at the next list refresh.
- **It works like the rest of the panel**: `↑ ↓ j k g G`, Page Up/Down,
  Home/End, `/` (title, repository, branch, result), `o`, `y`, `r`, `?`,
  Esc. Keys that do nothing on a pull-request row (`v`, `w`, `a`, `f`, `c`,
  `m`, `i`) say so, the way `v` and `w` do today on a row they do not fit.
- **From a check to its run** (open question 4): on an Actions check whose
  repository the repositories view shows, one key switches there with that
  workflow run selected, loading the run first if it is not cached; logs,
  watching and actions then work as today. Otherwise the panel says why.
- **Clear states**: "No open pull requests", a loading line, and the same
  error strip and hints as the repositories view (sign-in, permissions,
  rate limit, network).
- **Quota stays honest.** The pull-request reads' quota is tracked apart
  from the repositories' REST quota, so one never hides or speeds up the
  other; a rate limit on either pauses reads as today.
- **No cost while unused**: nothing is fetched until the view is first
  shown, and nothing while the panel is closed. The bar widget (#62) is
  unchanged.
- **An account change resets the view**: pull-request rows, expansion,
  filter, selection and pending reads are dropped, replies for the old
  account are ignored, and cached rows are not shown on reopen until the
  login is verified (as repositories are checked today). A `gh auth switch`
  while the panel stays open is noticed at the next open, as today.
- **Docs**: README (keys, refresh, errors, token permissions, limits) and
  the `keybindings.sh` sheet.

## Affected users and systems

- Everyone with the plugin: one new key and one new view; nothing changes
  until it is pressed.
- Token: reading pull requests and their checks needs read access to pull
  requests, check runs and commit statuses. The usual `gh auth login`
  token covers repositories it can see. Fine-grained tokens and
  organisations with single sign-on can hide some checks; the spec confirms
  the exact permissions against GitHub's docs, and the view shows "checks
  unavailable" instead of "no checks" when GitHub withholds them.
- Files: `actions.py` (new read kind, a fixed query, a parser that keeps
  only plain fields, GraphQL error and quota handling), `Polling.js` (new
  tasks, a separate quota), `ActionsModel.js` (rows, filter), `ActionsPanel.qml`
  (the view and keys), `keybindings.sh`, `README.md`, `tests/`,
  `manifest.json` (version).
- Hosts: p620 and razer through the usual release chain; p510 untouched.

## Constraints

- github.com only (#32 host pinning). Every new request is fixed in the
  helper; user text, logins and cursors are passed as validated values or
  query variables, never pasted into the query.
- All text from GitHub is plain text, cut to a length; only github.com
  links are opened or copied.
- Read-only: no new write; reruns stay where they are (#45).
- No polling while closed beyond today's watches; no storage, no token
  handling by the plugin.
- Bounded cost: one page of the list costs a fixed number of requests; the
  view must not starve repository polling.
- The QML smoke runs only in CI, never on the desktop.

## Open questions

1. **Which pull requests?** The issue says "of the listed repositories".
   - (a) Recommended: open pull requests you authored or are directly asked
     to review, across github.com, in one GraphQL request (one search with
     `OR`, or two searches in one request merged; the spec confirms which
     GitHub accepts). One request per refresh whatever the catalogue size.
     A pull request stays listed while a review request stands.
   - (b) Authored only, as gltui #40 did; review requests later.
   - (c) All open pull requests of every catalogue repository: closest to
     the issue's words, but at least one request per repository per
     refresh, which grows with the catalogue and competes with run polling.
2. **Which data, and how?** Recommended: GraphQL, with each pull request's
   head commit, its rollup state and up to the cap of its check runs and
   commit statuses in the same reply; GitHub's GraphQL points quota (5,000
   an hour, separate from REST) is read from the reply and tracked on its
   own, and errors inside a successful HTTP reply are handled. Alternative:
   REST only, which needs the search plus three requests per pull request
   (the pull request for its head, check runs, combined status): about 151
   requests for 50 pull requests.
3. **Key and caps.** Recommended: `p` switches views (not while typing in
   the filter; auto-repeat ignored); up to 50 pull requests and up to 50
   checks each.
4. **Jump from a check to its run.** Recommended: in scope, for Actions
   checks in catalogue repositories, with `Enter`/`l` on the check, loading
   the run by id when it is not cached. Out of scope would leave only `o`.
5. **Bar widget.** Recommended: unchanged; pull-request failures are not
   counted in the bar (a later issue could add them).
