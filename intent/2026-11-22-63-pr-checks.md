# Intent: A pull-request checks view in the panel

## Problem

The panel shows workflow runs per repository and nothing about pull
requests. To see whether your pull request's checks pass, or what is still
running on one you were asked to review, you leave the panel for GitHub.
Issue #63 (split out of #46 by the owner on 2026-11-16) asks for the check
status of open pull requests and says it needs its own intent because it
adds a new kind of request and has to fit the request budget.

What the code does today:

- **The helper reads only fixed REST endpoints** (`actions.py`
  `page_endpoint`): the account (`user`), the repository catalogue
  (`user/repos`), and a repository's workflow runs, one run, and a run's
  jobs. Every call goes through `gh api --hostname github.com`
  (`request()`). There is no pull-request, check-run, commit-status,
  search or GraphQL call.
- **A pull request's checks are not a list of Actions runs.** GitHub rolls
  them up per head commit from check runs (Actions and other GitHub Apps)
  and from commit statuses (older integrations). Matching cached Actions
  runs to a pull request by commit would miss every non-Actions check, and
  the run cache holds only each repository's newest 30 runs.
- **Requests share one budget.** `Polling.js` sends one request at a time,
  at most 60 a minute (`TIMING.perWindow`), slows down below 1,000 and 300
  remaining requests, and pauses every read on a rate limit. The panel
  polls only while open, except watched runs (#44).
- **The panel has one view.** Rows are repositories, runs, jobs and steps
  (`ActionsModel.js` `rows()`). `/` filters, `o` opens on GitHub, `y`
  copies a link, `r` refreshes. The `p` key is free.
- **The sister plugin solved the same request for GitLab** (nixarchy-gltui
  #40, v1.15.0): a second view, switched with one key, that lists your open
  merge requests across projects with their head-pipeline status, refreshed
  in the shared budget, and fetches nothing until first shown.

## Proposed outcome

When this is done, from the open panel and with the keyboard only:

- **One key switches** between the repositories view and a pull-request
  view, and back. The header says which view is shown. Switching back
  keeps what was expanded, filtered and selected in the repositories view.
- **The view lists open pull requests** (which ones is open question 1),
  most recently updated first, up to a cap; when there are more, the last
  row says so. Each row shows the repository, `#N`, the title, the head
  branch, a draft mark and the overall check result (pass, fail, running,
  or none) with the panel's usual icons and colours.
- **A pull request expands to its checks**, each with its name and result
  (pass, fail, running, skipped or neutral), whichever system reported it
  (open question 2). `o` on a check opens its page on GitHub; `o` on a pull
  request opens the pull request.
- **The result is never guessed.** A row says the result, "not checked"
  (not fetched yet), "no checks" (GitHub reports none), or how old its
  result is when older than its refresh target.
- **It stays current while you look, best effort.** Pull requests with
  running checks are refreshed in the shared budget behind selected data;
  finished results are rechecked on a bounded interval and on `r`.
- **It works like the rest of the panel**: `↑ ↓ j k g G`, Page Up/Down,
  Home/End, `/` (title, repository, branch, result), `o`, `y`, `r`, `?`,
  `q`, Esc. Keys that do nothing on a pull-request row (logs, watch, rerun,
  cancel) say so in the footer.
- **From a check to its run.** When a check is an Actions run in a
  repository the repositories view shows, one key jumps there with the run
  selected, where logs, watching and actions already work (open question
  4). Otherwise the footer says why and `o` still opens it.
- **Clear states**: "No open pull requests", a loading line, and the same
  error strip and hints as the repositories view (sign-in, permissions,
  rate limit, network).
- **No cost while unused**: nothing is fetched until the view is first
  shown, and nothing while the panel is closed. Its requests go through
  the same scheduler, window and quota slowdown, and a rate limit pauses it
  like any other read.
- **An account change resets the view**, as it resets repositories today.
- **Docs**: README (keys, refresh, errors, limits) and the `keybindings.sh`
  sheet.

## Affected users and systems

- Everyone with the plugin: one new key and one new view; nothing changes
  until it is pressed.
- Token: reading pull requests and their checks needs read access to pull
  requests, check runs and commit statuses. The usual `gh auth login`
  token (classic scopes with `repo`) has it; the exact fine-grained token
  permissions are to be confirmed in the spec against GitHub's docs. The
  README must say what a token without them shows.
- Files: `actions.py` (new read kinds and a parser that keeps only plain
  fields), `Polling.js` (new tasks in the budget), `ActionsModel.js` (rows
  and filter), `ActionsPanel.qml` (the view and keys), `keybindings.sh`,
  `README.md`, `tests/`, `manifest.json` (version). The bar widget (#62)
  stays as it is.
- Hosts: p620 and razer through the usual release chain; p510 untouched.

## Constraints

- github.com only, as everywhere in the plugin (#32 host pinning); every
  new endpoint is fixed in the helper, with only validated numbers, names
  and cursors filled in.
- All text from GitHub is shown as plain text and cut to a length.
- Read-only: no new write; reruns stay where they are (#45).
- No polling while closed beyond today's watches; no storage, no token
  handling by the plugin.
- Stay within the shared budget: the view must not starve repository
  polling, and a page of the list must cost a bounded number of requests.
- The QML smoke runs only in CI, never on the desktop.

## Open questions

1. **Which pull requests?** Recommended: open pull requests you authored or
   are asked to review, on github.com, found with one search (the gltui
   #40 shape; covers repositories outside the catalogue). Alternative: all
   open pull requests of every catalogue repository (the issue's wording,
   "of the listed repositories"): one request per repository per refresh,
   which grows with the catalogue and competes with run polling.
2. **Which data, and how?** Recommended: one GraphQL request per page that
   returns the pull requests with their head commit's check rollup
   (`statusCheckRollup`, both check runs and commit statuses), with a fixed
   query in the helper; GraphQL has its own points quota, which the
   helper reports like the REST quota. Alternative: REST only, a search
   request plus two per pull request (`check-runs` and `status` of the head
   commit), which costs more requests and is closer to the existing code.
3. **Key and cap.** Recommended: `p` switches views; up to 50 pull requests
   and up to 50 checks each, with "N more on GitHub" past either cap.
4. **Jump from a check to its run.** Recommended: in scope, for Actions
   checks in catalogue repositories (`Enter` or `l` on the check); out of
   scope would leave only `o`.
5. **Bar widget.** Recommended: unchanged; pull-request failures are not
   counted in the bar (a later issue could add them).
