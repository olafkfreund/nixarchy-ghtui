# Intent: Remove the panel's dead code and duplicated logic

## Problem

The panel runs the helper in one way only:
`python3 actions.py page '<json>'` (ActionsPanel.qml line 154). Everything
else the helper can do is left over from before smart polling (#9), and
there's a little dead state and repeated logic on the QML/JS side too.
Line numbers below are from `main` at 4f51f7f.

**actions.py: modes nothing calls.**

- The `summary`, `jobs`, `repositories` and `activity` modes, and the
  functions that only they use: `api()` (lines 42–53), `pages()`, `runs()`,
  `repositories_page()`, `activity()` and `summary()` (195–249), and their
  branches in `main()` (272–286).
- They repeat logic that page mode already has. `repositories_page()`
  repeats the catalogue projection in `read_page()` (174–175). `runs()`
  repeats the status sort that Polling.js does (136, 217). `api()` repeats
  the error classification in `read_page()` (157–166), with different
  wording.
- Six tests in `tests/test_actions.py` (lines 15–53) only test those
  functions. Two more, `test_cancellation_reaps_gh` and
  `test_missing_gh_is_json_error` (61–87), run `actions.py summary`, but what
  they check (SIGTERM reaps the `gh` child, and a missing `gh` gives a JSON
  error) also applies to page mode.

**actions.py: a deadline that isn't needed any more.** `main()` sets a
90-second `SIGALRM` that raises `DeadlineExceeded` (16–17, 258–266, 294). It
was there to limit a multi-page, multi-repository scan. Page mode makes one
`gh` call, and `request()` already limits it with `communicate(timeout=25)`
and kills the child. The `SIGTERM` handler is still needed: closing the panel
depends on it.

**Polling.js and ActionsPanel.qml: dead state.**

- `r.history = true` (Polling.js 220) is set and never read.
- `property var manifest` (ActionsPanel.qml 14) is never read in this repo.
- `open(payload)` (44) never uses `payload`. `toggle()` passes `"{}"`, and
  `omarchy-shell shell summon|toggle … '{}'` passes one too.
- `repositories` (17, set at 135) is just `repos.map(r => r.repo)`. It's only
  read for its length, in the header (268, 301) and in `status()` (62).
- `loading` (31) is an alias for `workerBusy`. The panel never reads it;
  only `tests/qml-smoke.py` (119, 126) does.

**Polling.js: the same logic twice.** The sort that puts running first and
then newest first, and the trim to ten completed runs (keeping expanded
runs), appear in `mergeRuns()` (136–138) and again at the end of a summary
in `complete()` (217–219).

**Timing numbers in two places.** The intervals (5 s, 10 s, 15 s, 60 s,
10 min, the 250 ms settle, 5 min catalogue age, the 60-per-minute and
1-second limits, and the backoffs) are written straight into Polling.js
(27, 34, 66, 71, 83, 90, 96–97, 161, 175). The README's polling section
(152–168) repeats them. If one changes, nothing forces the other to change.

**The `repositories` key in shell.json.** `configure()` (ActionsPanel.qml
119–128) reads `plugins[].repositories` from `~/.config/omarchy/shell.json`
and seeds the list before discovery. The README gives it one sentence (line
125, "Legacy `repositories` settings are startup hints only"). No example
or schema shows it. When the catalogue finishes, Polling.js (205–206) drops
any seeded entry that the catalogue doesn't return, so the key can't add a
repository. All it does is show some names a moment sooner.

**The legacy menu-key migration.** `registered_menu()` in menu.py (64–81)
moves `system.github-actions` / `github-actions` to `apps.github-actions`.
It came in with #11 (b605db3, version 0.3.1), and `tests/test_menu.py`
(47–57, 82, 139) tests it. The issue says to remove it "after a release".
There hasn't been one. The repository has no git tags and no GitHub
releases. `manifest.json` has gone from 0.3.1 to 0.4.0 (#13, bbcbc69), but
nothing was tagged or published, and #20 shows that razer was migrated by
this code. So by the issue's own rule it isn't time yet, unless you decide
that the 0.4.0 bump counts as a release.

## Proposed outcome

- Nothing changes for users. The panel sends the same requests at the same
  times, and shows the same rows, errors and timers.
- `actions.py` accepts only `page`. The four old modes, the functions that
  only they use, `DeadlineExceeded` and the `SIGALRM` deadline are gone,
  about 95 of its 299 lines. `SIGTERM` handling is kept.
- The six tests of old functions are deleted, about 40 lines. The
  cancellation and missing-`gh` tests run page mode and still check the same
  things.
- `r.history`, `repositories` (the header and `status()` use
  `repos.length`) and `loading` (qml-smoke reads `workerBusy`) are removed.
  `manifest` and the `payload` parameter go too, unless the host needs them
  (see open questions).
- The sort-and-trim exists once in Polling.js, and both places use it.
- The timing numbers are named constants in one block at the top of
  Polling.js. The README refers to them or is checked against them, so the
  two can't drift apart.
- The `repositories` key is either documented properly or removed,
  depending on the answer below.
- The menu migration is kept or removed, depending on the answer below.
- In total about 145 lines are removed, most of them the ~135 lines of
  Python and tests.

## Affected users and systems

- Anyone who runs `actions.py summary|jobs|repositories|activity` by hand
  or from a script. Those commands will now fail with an argparse usage
  error. None of them are documented in the README, and no Nixarchy
  component calls them.
- Anyone with `repositories` in `shell.json`, if the key is removed. The
  panel then ignores it, and discovery works as it does today.
- Anyone who still has a `system.github-actions` or `github-actions` menu
  entry, if the migration is removed. The entry stays where it is, and
  `apps.github-actions` is added alongside it.
- Files: `actions.py`, `Polling.js`, `ActionsPanel.qml`, `README.md`,
  `tests/test_actions.py`, `tests/qml-smoke.py`, perhaps `tests/polling.cjs`,
  and `menu.py` / `tests/test_menu.py` if the migration goes.
- Open PRs #26 (#22), #27 (#23) and #28 (#24) change ActionsPanel.qml.
  #28 also changes ActionsModel.js, Polling.js, actions.py and the tests.
  #28 changes `main()` for page mode: it gives `DeadlineExceeded` its own
  `errorType`, and adds `test_old_mode_error_unchanged`, which checks the
  old `jobs` mode. Implementation starts after all three are merged, and
  is rebased on the result. That test and #28's handling of
  `DeadlineExceeded` are then removed along with what they cover.

## Constraints

- No change a user can see. The request sequence, timings, error texts and
  error types (`errorType`) stay exactly as they are for the panel.
- `SIGTERM` still reaps the `gh` child, and a test proves it.
- A request stays limited to 25 seconds.
- All suites pass: `python3 -m unittest discover -s tests -v`,
  `node tests/model.cjs`, `node tests/polling.cjs`, and
  `tests/qml-smoke.py` where a display is available.
- `nix flake check` passes.
- Only removal and consolidation. No new features or behaviour. Anything
  that turns out not to be dead stays, and the plan says why.

## Open questions

1. **The `repositories` key.** Should it be removed, since discovery makes
   it redundant and prunes it anyway? Or kept and properly documented as a
   startup hint? Or changed to pin repositories so they survive pruning,
   which would be new behaviour and belongs in a separate issue?
2. **The menu migration.** Should it be removed now, or kept until a release
   is tagged? There are no tags or releases. I suggest keeping it and
   tagging `v0.4.0` or later, so a later issue can remove it.
3. **`manifest` and `open(payload)`.** Nothing in this repo reads them, but
   omarchy-shell may set `manifest` on every plugin and pass a payload to
   `open`. Should I check the omarchy-shell plugin loader before removing
   them, and keep them if they're part of its interface?
4. **Timing numbers in the README.** Should the README keep its table and
   have a test check it against the Polling.js constants? Or should it name
   the constants and drop the numbers?
5. **The old modes.** Should they be deleted outright, or should they exit
   with a short message that points to `page`? I suggest deleting them:
   argparse already rejects them with a usage error.
