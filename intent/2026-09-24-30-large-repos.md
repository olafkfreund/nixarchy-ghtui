# Intent: Large repositories keep the panel responsive

## Problem

The panel keeps every run that isn't completed, with no limit. A repository
with thousands of queued or pending runs can stall the panel when you expand
it. Spammed fork pull requests or a concurrency backlog can both cause this.

What the code does today:

- **The cap only covers completed runs.** `Polling.js` sorts running and
  queued runs first, then drops completed runs after the tenth
  (`mergeRuns`, lines 136-138, and the end of a summary snapshot,
  lines 216-219). The filter keeps every run whose status isn't `completed`,
  so every queued, waiting, pending, requested and in-progress run stays in
  memory.
- **The helper fetches all of them.** When you select a repository,
  `Polling.js` runs a summary task. It goes through six phases: `recent`,
  `in_progress`, `queued`, `waiting`, `pending` and `requested`
  (line 2). `actions.py` fetches `recent` as one request of 10
  (`page_endpoint`, line 76). Each other phase uses
  `?status=<s>&per_page=100` and follows GitHub's `Link: rel="next"` header
  until there are no more pages (`read_page` line 188, `next_page`). Each
  page is one `gh api` process.
  - The cost of one snapshot is `1 + Σ max(1, ⌈runs in that status / 100⌉)`
    requests. With nothing queued, that's 6. With 2,000 queued runs, it's
    25.
  - Every request is spaced at least one second apart, with at most 60
    requests a minute (`next`, line 97). So a snapshot of 2,000 queued runs
    takes at least 25 seconds. It then runs again 60 seconds after it
    finishes. That's about 1,000 of the hourly 5,000 REST requests for one
    selected repository.
  - GitHub's REST documentation says the list-runs endpoint returns at most
    1,000 results when you filter by `status`. If that's true, each phase
    stops at 10 pages, and runs past that point are dropped without any
    sign. The spec must confirm this.
  - `actions.py`'s older `summary` mode also pages through every active
    status (`runs`, lines 209-218). The panel doesn't call that mode.
- **Every page rebuilds the whole list.** `receivePage` →
  `Polling.complete` → `adopt()` → `rebuild()` (`ActionsPanel.qml` lines
  133-140). `rebuild()` calls `Model.rows()`, which creates one row per run
  in each expanded repository. It then calls `Model.syncRows()`
  (`ActionsModel.js` lines 77-98), which:
  - searches the `ListModel` forward from `i` for each row's key. That's
    linear when rows are in order, but quadratic when rows move around.
  - compares each kept row with `JSON.stringify(old) !==
    JSON.stringify(new)`, which means two serialisations per row, every
    rebuild.
- **With PR #27, this runs every second.** PR #27 (#23, not merged yet) adds
  `onNowChanged: rebuild()`, so the full rebuild runs every second while the
  panel is open, as well as after every page. The #23 work measured about
  7 ms per tick at 1,650 rows when rows stay in order.

Measured in Node 26 on p620 (median). The test repository has N queued runs
with a `run_started_at` time plus 10 completed runs, and is expanded. The
`ListModel` is an array stand-in, so the real QML `ListModel` (property
wrappers, delegate updates, layout) will only be slower.

| Queued runs | Rows | `rows()` | First build (`rows`+`syncRows`, empty model) | One tick (`rows`+`syncRows`, rows in order) | Rows reordered (`syncRows`, reversed) |
| ----------: | ---: | -------: | -------------------------------------------: | ------------------------------------------: | ------------------------------------: |
|       1,000 | 1,012 |  2.7 ms |  2.8 ms |  4.7 ms |  10.9 ms |
|       2,000 | 2,012 |  5.1 ms |  4.7 ms |  9.9 ms |  37.2 ms |
|       5,000 | 5,012 | 13.2 ms | 12.2 ms | 26.0 ms | 212.8 ms |

A tick where nothing changed costs as much as one that changes every row,
because the `JSON.stringify` comparison dominates. At 5,000 rows, one tick
takes more than a 60 Hz frame (16.7 ms) in Node alone. The reordered case
shows the quadratic search. The panel also creates a `ListModel` row, and
keeps it, for each of those runs, even though only a screenful is visible.

A collapsed repository costs nothing in `rows()`, which returns early. So
this only shows up when you expand the busy repository. But the fetching
and memory costs are there as soon as you select it.

## Proposed outcome

- Expanding a repository with thousands of queued or pending runs doesn't
  stall the panel. Keys, scrolling and search stay smooth while it polls
  and while the one-second timer ticks.
- The number of run rows shown for each repository has a limit, so the cost
  of each rebuild no longer grows with the size of a repository's backlog.
- In-progress runs still appear first. When runs are hidden, the panel says
  so and shows how many, for example "+1,843 more queued · open on GitHub".
  The panel never hides them without telling you.
- The number of requests for one snapshot of a busy repository has a
  fixed ceiling, so one repository can't use up the request budget or delay
  updates for the other repositories.
- A repository that isn't busy looks and behaves the same as today.

## Affected users and systems

- Anyone who opens the panel for a busy repository: large organisations,
  public projects that get fork pull requests, and repositories that use
  concurrency groups and build up a queue.
- `Polling.js` (`mergeRuns`, summary snapshot, possibly the phase list),
  `ActionsModel.js` (`rows`, `syncRows`), `ActionsPanel.qml` (`rebuild`,
  status line), and maybe `actions.py` (`page_endpoint`, paging).
- `tests/polling.cjs`, `tests/model.cjs`, `tests/test_actions.py`, and
  `tests/qml-smoke.py`.
- It interacts with PR #27 (#23 live timers). The one-second rebuild it adds
  is the main reason this cost grows, so the fix must stay fast with that
  change merged.

## Constraints

- **Running runs come first, and what's shown must be correct.** In-progress
  runs stay at the top, followed by other runs that haven't completed, then
  the 10 latest completed runs. Every visible row shows its real current
  status. An expanded run, a run marked `awaitingFinal`, or the run you're
  inspecting must never be dropped (both cap filters keep them today). Any
  count the panel shows must be accurate, or say that it's approximate.
- **API budget.** Keep the current limits: at least one second between
  requests, at most 60 a minute, and the rate-limit and cooldown handling.
  A busy repository must not increase requests without limit, and must not
  delay the activity checks for other repositories.
- **No extra dependencies.** Plain JavaScript in the QML engine, Python
  standard library plus `gh`, and Node for tests. No new QML modules,
  packages or build step.
- Selection and scroll anchoring in `rebuild()` still work: the selected row
  and the top visible row stay where they are.
- Search, currently a substring match over every run in `rows()`, must still
  find runs. The approver decides whether search also looks at hidden runs
  (see the open questions).

## Open questions

1. **Cap value.** How many runs that haven't completed should be shown for
   each repository? For example: 50, 100 (one API page), or 200. Should
   in-progress runs have no limit, with only queued, waiting, pending and
   requested runs capped?
2. **Hidden runs.** What do you see when runs are hidden? A summary row with
   counts by status that opens the Actions page on GitHub, a "show more" row
   that raises the cap for that repository, or both?
3. **Fetch limit or display limit.** Should the panel stop fetching after
   the first page (or N pages) of each status, which saves requests but
   makes the hidden count come from `total_count`, or keep fetching
   everything and limit only the rows it shows?
4. **Search.** Does a search look only at the visible runs, or at every
   cached run?
5. **Order and dependency with #23.** Should this land before PR #27, or
   should #27 merge first and this work measure against the one-second
   rebuild? Is making `syncRows` cheaper (for example, comparing only the
   fields that change instead of `JSON.stringify`) in scope here, or a
   separate issue?
