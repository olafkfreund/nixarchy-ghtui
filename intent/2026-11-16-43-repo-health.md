# Intent: Repo rows show their last result, and failing repos come first

## Problem

The panel can tell you what is running. It cannot tell you what is broken.
A repository whose last run failed looks the same as a healthy one: both
read "0 running". You have to expand the repository and read the runs to
find out.

What the code does today:

- **A repo row has no result to show.** `ActionsModel.js` builds the row
  `info` text as `active + " running"`, or "archived", "disabled",
  "unavailable" or "not checked" (line 48). The row `status` is only
  `in_progress`, `neutral` or `error` (line 47), where `error` means the
  repository could not be read, not that its CI failed. Failure icons and
  colours exist (`icon()` in `ActionsModel.js` lines 17-24, `statusColor`
  in `ActionsPanel.qml` line 166), but they are only used on run rows.
- **Most repos have no conclusion unless a run was seen going.** Only the
  selected repository gets a summary task, which fetches `?per_page=10`
  (`actions.py` lines 77-79; `Polling.js` line 69). Every other repository
  is polled with an `activity` task, which `actions.py` turns into
  `status=in_progress` (line 77). That response holds only runs that are
  still going. A run first seen in progress is looked up again when it
  disappears (`Polling.js` lines 150-158), so its conclusion does arrive.
  A run that was never seen in progress never does.
- **Short runs can be missed.** An idle repository is checked every ten
  minutes (`TIMING.idle: 600000`, `Polling.js` line 4; used at line 74).
  A two-minute run that starts and ends between two checks can go
  unseen, so the panel shows "0 running" and no sign that CI ran or
  failed. This is finding 7 in the Codex review. The README also records
  a 168 second idle cold scan, from a simulation, not a live run
  (`README.md` line 179).
- **Only 10 recent runs, and "last" is by run id.** A selected repository
  keeps 10 completed runs, plus any run the user has expanded or inspected
  (`recent()` and `kept()` in `Polling.js` lines 141-148; the fetch is
  `per_page=10`, `actions.py` line 79). The fetch is not filtered to
  completed runs. Runs are ordered by id (`Polling.js` line 143), not by
  completion time. A busy repository can push a failure out of that window
  within minutes.
- **Repos are sorted by running count only.** `rows()` sorts by
  `b.active - a.active` (`ActionsModel.js` line 38). Repositories with
  nothing running keep the order the catalogue gave them (pushed-at order),
  so a repository that just failed can sit far down a long list.
- **Search is a plain substring.** The filter lowercases the text and
  matches it against the repository name and description, and against each
  run's name, title, branch and state (`ActionsModel.js` lines 38-41). You
  cannot ask for "failed runs only", or runs on one branch, by one actor
  or from one event.

## Proposed outcome

These hold whichever way the open questions are answered.

- A repository row says how its most recent known run ended and how old
  that information is, in addition to "N running". A user can read both
  from the row without expanding it.
- A repository whose most recent known run failed is visibly marked as
  failing, and it is listed ahead of repositories that are healthy. The
  order within a group is stable between refreshes.
- A repository the panel has not looked at yet, or whose last check
  failed, is never shown as healthy. Stale information is shown as stale.
- Archived, disabled, unavailable and not-checked repositories still
  appear, in a place the user can predict, and are not taken for failing
  or healthy.
- Searching can narrow the list to failed runs and to a branch, an actor
  or an event, and plain text still works as it does today.
- A selected repository shows more past runs than it does today, and the
  panel says how many.
- The cost of learning results is stated as requests per hour for N
  repositories, before and after, and stays inside the existing limits.

## Affected users and systems

- Anyone who uses the panel to see whether CI is green across many
  repositories, which is its main job. The people most affected have
  dozens of repositories and an idle list that is mostly unchanged.
- `ActionsModel.js` (`rows`, `info`, `status`), `Polling.js` (task kinds,
  `TIMING`, `activity`, `recent`), `actions.py` (`page_endpoint`, task
  kinds), `ActionsPanel.qml` (list rendering, `statusColor`, search
  placeholder, help line).
- `tests/model.cjs`, `tests/polling.cjs`, `tests/test_actions.py` and
  `tests/qml-smoke.py`. `README.md` and the keybinding help line if search
  behaviour changes.
- It interacts with #30 (limits on large repositories, which already caps
  and counts hidden unfinished runs) and #23 (live timers, whose
  one-second rebuild makes every row cheaper to compute the better).

## Constraints

- **Rate limit is the main constraint.** A new request per repository per
  poll multiplies across the whole catalogue. Today an idle repository
  costs one request every ten minutes. Any change that learns a repository's
  last result must be measured against that, and still stay inside the
  existing limits (one second between requests, 60 a minute, the rate-limit
  and cooldown handling). It must not slow the activity checks that already
  run, and it must not use up the hourly budget on repositories the user
  does not look at.
- **No daemon.** The panel polls only while it is open. Notifying you of a
  failure while the panel is closed is out of scope.
- **No token storage.** The panel still uses `gh`'s own authentication and
  never sees or keeps a token.
- **Argument arrays, not shell strings.** The helper is still started with
  an argument array, and nothing typed in search reaches a shell.
- **Untrusted GitHub text stays sanitised (#32).** Any new GitHub text the
  panel shows or searches, such as actor or event names, must get the same
  plain-text filtering as the run fields `actions.py` already cleans
  (`RUN_TEXT`, line 42). The helper passes other fields through unchanged
  (line 195), so this is not automatic.
- **github.com host stays pinned (#32).** The existing host and endpoint
  checks in `actions.py` must still apply to any new request.
- **Theme-native and keyboard-first.** Colours come from `Color`, as
  `statusColor` does. No new key is needed to read the result, and every
  new view is reachable without a mouse.
- **Stays read-only, no new dependencies.** Nothing is sent to GitHub other
  than GET reads. Plain JavaScript, Python standard library plus `gh`,
  Node for tests.
- **What this bends.** Today the panel samples activity only. Showing a
  result for repositories that are not selected means fetching completed
  runs for them. The "an idle repository costs one request" budget is the
  design this task changes, and the spec must say by how much.
- Existing tests keep passing, and stale-reply rejection (`requestId` and
  `generation`) is unchanged.

## Open questions

1. **Which repositories get a known last result, and how fresh must it be?**
   Every repository, or only ones the user chooses to watch? How old may a
   result be before the row calls it stale? Cooldowns and rate limits can
   delay checks, so say what the user is promised when they do.
2. **Must a failure that is no longer the latest still show?** A failed run
   followed by a pass between two checks would be hidden by a "last result"
   view. Is that acceptable, or must a recent failure stay visible for a
   while? This decides how much history is needed.
3. **Is "failing" the last run of any kind, or only on the default branch?**
   A failed pull-request run on a feature branch may or may not make the
   repository "failing". Or both, shown differently.
4. **What counts as failed?** Only `failure`, or also `timed_out`,
   `startup_failure` and `cancelled`? The model today draws the first
   three as failures and `cancelled` as neutral (`ActionsModel.js` lines
   19-21). And is "last" by start time, run id or completion time?
5. **How often are idle repositories checked?** Keep ten minutes and
   accept that short runs can be missed, check sooner for some
   repositories, or let the user decide.
6. **How many past runs, and who chooses?** A fixed larger number, or the
   user's choice? A larger number costs rows (see #30) and request size.
7. **How is the list arranged?** Labelled sections the user moves across,
   or only a different order with a marker? Are empty sections hidden?
   Where do archived, disabled, unavailable and not-checked repositories go?
8. **What can search filter on?** Which of branch, actor, event, result
   and running state? Do filters apply only to runs already held, or may
   they cause new requests? How do they combine with each other and with
   plain text?
9. **One change or several?** The issue lists five wants (last result,
   sort, grouping, more runs, search filters). Should this be one spec, or
   split so the parts that need no new requests can ship before the parts
   that do?
