# Intent: Run actions from the panel

## Problem

The panel can show a failed or stuck run, but it cannot do anything about it.
To rerun a job, cancel a run that is burning minutes, or start a manual
workflow, you leave the panel, open GitHub or a terminal, find the same run
again and act there. Issue #45 asks for the panel to do the common ones
itself: rerun, rerun failed jobs, cancel, and start a `workflow_dispatch`
run. Approving pending deployments is a possible extra.

Today the plugin has no write path at all. What the code does:

- **The helper can only read.** `actions.py` says "Read-only GitHub Actions
  data" (line 1). Its only mode is `page` (`main`, line 213). `request()`
  runs `gh api --hostname github.com <endpoint>` with no method or body
  (lines 45-47), so it can only issue GET requests.
- **The endpoint list is closed.** `page_endpoint` accepts five task kinds
  (`catalogue`, `activity`, `summary`, `jobs`, `run`, line 60) and builds only
  read URLs for repositories, runs and jobs (lines 59-86). Anything else
  raises `ValueError`. There is no kind for a rerun, a cancel or a dispatch,
  and no workflow list to pick a dispatch target from.
- **Documented permission is read only.** The README requires `gh`
  "authenticated for your repositories with Actions read access" (line 22).
  The authentication section says fine-grained PATs need Metadata read and
  Actions read (line 129). A token that works today may not be allowed to
  write.
- **A permission error is read as "cannot read".** A 403 or 404 becomes
  `errorType="permission"` with the text "Resource unavailable or Actions
  read permission missing" (`actions.py` lines 166-167). Rate-limit replies
  are sorted out first (lines 162-165). For catalogue, activity and summary
  tasks, the scheduler then marks the whole repository `blocked` until a
  manual refresh (`Polling.js` lines 187-188). A refused write must not be
  reported this way, or one failed rerun would hide the repository's
  activity.
- **The panel has no way to ask or report an action.** It does have a search
  text field (`ActionsPanel.qml` line 265), but no confirm step and no place
  to show the result of an action. The only status text is the search
  placeholder, which carries errors and cooldowns (lines 292-293). The
  footer hint lists move, expand, search, refresh, repos, GitHub and close
  (line 374). The key handler has `r`, `R` and `o` taken (lines 248-251).
- **A write that gets cut off has an unknown result.** The helper kills its
  `gh` child after 25 seconds (`actions.py` lines 50-52) and closing the
  panel stops the running request (`ActionsPanel.qml` lines 54-57). A reply
  that arrives after the panel moved on is discarded (`Polling.js`
  `complete`, line 167). For a read that is harmless. For a write, a killed
  call does not prove GitHub did nothing, and a blind retry could start the
  action twice.
- **The panel already spots a rerun.** `Polling.js` compares `run_attempt`
  and drops cached jobs when it changes (`invalidateJobs`, lines 125-129).
  So a rerun shows up on the next poll, but only when the scheduler gets to
  it. That is gated by a server cooldown and a per-window request ceiling
  (`next`, lines 97-100). Nothing triggers a refresh right after an action.
- **Rows move while you look at them.** Polling rebuilds and reorders the
  list. A confirm step that points at "the selected row" could end up
  pointing at a different run by the time you press the key.

## Proposed outcome

When this is done, from the panel and with the keyboard only, you can:

- Rerun the selected run, or rerun only its failed jobs.
- Cancel the selected queued or running run.

Whether starting a `workflow_dispatch` run is also part of this change, and
how it takes inputs, is for the owner to decide (open questions 1 and 2).

Whichever way the questions are answered:

- Every action asks for confirmation first, naming the repository, the run
  or workflow, and what will happen. Nothing is sent until you confirm.
  Escape backs out.
- The confirmation applies to exactly the run or workflow it named. If the
  list changes while the confirmation is open, you cannot confirm an action
  on a different target.
- After you confirm, the panel tells you whether GitHub accepted the action,
  refused it, or whether the outcome is unknown (timed out or cut off). In
  the unknown case it says so and does not retry on its own.
- A refusal (no write permission, run already finished, workflow without a
  dispatch trigger) names the cause. It does not mark the repository
  blocked and does not stop polling.
- Actions that make no sense for the selected row are not offered: you cannot
  cancel a completed run or rerun a running one.
- When the normal refresh is held back by a rate-limit cooldown, the panel
  says so instead of showing stale state silently. A manual refresh still
  never bypasses a server cooldown.
- The README and the keybindings reference list the new keys, say that the
  plugin can now write, and say which token permission that needs. A token
  with read access only still works for everything that works today.

How quickly the affected run is refetched, and whether approving pending
deployments is included, are open questions 8 and 4.

## Affected users and systems

- **Everyone who has the plugin installed.** The panel stops being
  read-only. Users with a read-only `gh` login keep today's behaviour and see
  a clear message if they try a write.
- **Fine-grained PAT users** need Actions write on the repositories they
  want to act on. Classic tokens and org rules (SSO, branch and environment
  protection) may also matter. The spec must confirm the exact requirements
  against GitHub's documentation.
- **Files touched.** `actions.py`, `ActionsPanel.qml`, `ActionsModel.js`,
  `Polling.js`, `README.md` (Requirements, Authentication, Keyboard),
  `keybindings.sh` (the installed keys reference), and tests under `tests/`.
- **Rate limits.** Write requests spend the same GitHub quota as polling.
  The scheduler caps itself at `TIMING.perWindow` requests per window
  (`Polling.js` lines 4 and 100). Whether an action counts against that
  ceiling is a design question.
- **GitHub side effects.** A rerun or dispatch starts real, billable
  runner time and can trigger deployments. A cancel cannot be undone.

## Constraints

Kept as they are:

- **No daemon, no database, no token storage.** The plugin never reads or
  stores the token; `gh`'s own login does the signing (README line 3).
- **Theme-native and keyboard-first.** Any new confirm step or input uses
  the Omarchy theme and works with keys alone. The README says "No buttons"
  (line 3).
- **No shell strings.** `request()` passes an argument list to `Popen`
  (line 46). Anything the user types, such as dispatch inputs, must reach
  `gh` without being able to change what the command does or read local
  files. The spec must show how.
- **github.com only.** Writes go to the same pinned host as reads, and
  repository, run and workflow identifiers are validated like the existing
  ones (`repo_name` line 19, run ID check lines 70-72).
- **GitHub text is untrusted (#32).** Workflow names, run titles, branch
  names and error messages shown in a confirmation or result are sanitised
  with `plain()` (line 27) and drawn as plain text.
- **Polling rules still hold.** No polling while closed; a manual refresh
  never bypasses a server cooldown (README, Refresh and errors).

Changed by this task:

- **"Read-only" is dropped.** The module docstring, the README intro and
  the "Actions read access" requirement all change. The set of requests the
  helper will send stays a closed list, not a way to send any request.
- **A write is not a read.** It must be distinguishable from a page fetch in
  how its result is reported and how its failures are handled, including the
  permission case: for a write a 403 means "tell the user", not "stop
  reading".

Not changed: the pinned host, the sanitising of GitHub text, and the
existing read behaviour.

## Open questions

1. **Which actions ship in the first change?**
   - (a) Rerun, rerun failed, cancel only.
   - (b) Those plus `workflow_dispatch`.
   - (c) All of (b) plus approve pending deployments.

   Dispatch needs a workflow list and a way to choose a branch or tag and
   give inputs, which the panel has no flow for. That is much more work than
   the other three.

2. **If dispatch ships, which workflows can you start?**
   - (a) Any workflow that supports manual dispatch, including ones that
     declare inputs, with the panel collecting them.
   - (b) Only workflows that need no inputs. For the rest you go to GitHub
     or a terminal.

3. **How strong is the confirmation?** Should every action need the same
   single yes/no, or should destructive ones (cancel) ask for more, such as
   typing the repository name?

4. **Should approving deployments be in scope at all?** It can release a
   production deployment. If yes, does it need a stronger confirmation than
   a rerun, and should it show the environment and allow a comment?

5. **How do you reach the actions?** Each action on its own key, or one key
   that offers a list of what the selected row allows? Today's `r`, `R` and
   `o` are taken, and keys that differ only by case are easy to hit by
   mistake.

6. **Can writing be turned off?** Should the write actions always be
   available when the token allows them, or can a user choose to keep the
   panel read-only? If a choice, where does it live, given the plugin keeps
   no state file?

7. **Do actions use the refresh budget?** Should a write count toward the
   per-window request ceiling and so possibly wait, jump the queue, or be
   exempt?

8. **How is the result shown, and how fast does the run refresh?** Should
   there be a dedicated result line, and should the affected run be
   refetched at once or at its normal interval? An answer must also cover
   the case where a cooldown holds the refetch back.

9. **What do users on a read-only token see?** Are the write actions shown
   and then refused with a message, or hidden after the plugin finds out the
   token cannot write? Finding out may cost a request and may not be
   reliable for fine-grained tokens.
