# Intent: Make the QML smoke test pass or fail deterministically

## Problem

`tests/qml-smoke.py` sometimes fails with `CHECK FAILED: timeout stage=1`.
On p620 it failed 1 in 8 runs on unchanged `main` (cf03943) and 2 in 8 on
the #31 branch. It passed 3 of 3 on razer. Every failure was the same
stage-1 timeout. Neither `nix flake check` nor CI runs it, so the flake only
shows up locally. But it is the only end-to-end check of the real QML worker,
and the #31 plan now allows one rerun. A gate that needs reruns is not a gate:
it hides real regressions in the same place the flake happens.

How the test works: an 18 s QML timer fails the run, whatever stage it is in.
A 1 s timer runs the synchronous stage-0 checks and opens the panel
(`stage=1`). A 250 ms timer then waits for three things: 6 or more requests,
jobs for `one/repo:7`, and a complete catalogue. The fake `actions.py`
sleeps 0.1 s per request, and `Polling.js` leaves at least 1 s between
request starts.

**Hypothesis 1 (most likely, not yet confirmed):** a single bad reply stops
polling for good. `ActionsPanel.qml` reads `pageOutput.text` (a
`StdioCollector`) inside `requestProc.onExited`. If Quickshell emits
`exited` before the collector has read all of stdout, the reply is empty or
cut short. `Model.reply` then turns it into a `setup` error ("Workflow helper
failed (exit 0)"), or `receivePage` rejects it as invalid data. Either way
`Polling.complete` sets `s.auth = true`, and `Polling.next` returns nothing
until a manual refresh. Stage 1 then waits until the 18 s timer fires. The
race between the process exiting and the pipe being read depends on load,
which would explain why p620, the busy working desktop, fails and razer does
not. If this is right, it is also a product bug. The real panel would stop
polling after one unlucky read and show a setup error.

**Hypothesis 2 (less likely):** the helper is just too slow under load. I
simulated the stage-1 schedule in Node against the real `Polling.js`, without
running QML. The run finishes after 6 requests, in about 5.2 s when each
helper call takes 150 ms and about 7.2 s when it takes 1.2 s. The budget
after stage 0 is about 17 s. To time out, each `python3` start would need to
take around 2.8 s.

The timeout message already prints `panel.status()`, but the failed runs'
output was not kept. The `error`, `requests`, `lastRequest` and `inFlight`
fields in that output tell the two hypotheses apart.

## Proposed outcome

- The smoke test passes on every run on razer, including under CPU load. It
  fails only when a check really fails, so no plan or review has to allow a
  rerun.
- When it fails, the output says why: which condition was missing and the
  panel status. It does not just say "timeout".
- The root cause is named and fixed where it lives. If it is Hypothesis 1,
  the fix goes in the panel's reply handling, and the real panel gets the
  fix too. Raising the timeout is not the fix.
- The #31 plan's rerun allowance can be removed.

## Affected users and systems

- `tests/test_actions.py` `test_cancellation_reaps_gh`, a second
  load-sensitive flake: it gives the fake `gh` 2 s to start and failed once
  under heavy load on p620 during #30. It is in scope here, under the same
  rule: fix the cause, don't just raise the timeout.
- `tests/qml-smoke.py`, and probably `ActionsPanel.qml` (`requestProc`
  reply handling). Possibly `Polling.js` if a stop needs a narrower
  trigger.
- Anyone running the smoke test as a gate for QML changes, currently the #31
  work.
- Users of the panel, if Hypothesis 1 holds, because the same race would stop
  live polling.
- Host **razer** for all desktop runs. Only pure-JS checks (Node against
  `Polling.js`) run on p620.

## Constraints

- All smoke-test and desktop runs happen on razer. The lead coordinates
  them. The smoke test does not run on p620, which is your working desktop.
- No new dependencies: Python stdlib, the existing Quickshell and Node
  tooling only. Load for the evidence runs comes from tools already on
  razer, for example busy shell loops or a parallel nix build, not
  `stress-ng`.
- The test must not contact GitHub. It keeps the fake `actions.py`.
- Keep the fix small. Timeouts must not grow to hide the race.

## Open questions

1. Before any design, may the lead collect evidence on razer? For example,
   about 50 loops of `python3 tests/qml-smoke.py` with and without CPU load,
   keeping the `panel.status()` line from each failure. An `error` of
   "Workflow helper failed (exit 0)" or "invalid data" confirms
   Hypothesis 1. An empty `error` with a stale `lastStarted` points to
   Hypothesis 2.
2. Should the smoke test also run in CI under a headless compositor (for
   example Hyprland or cage headless)? That is a bigger change, with a new
   CI job, a compositor inside the runner, and the Omarchy theme and shell
   paths it expects. Should it be a separate issue, or part of #29?
3. Stage 0 has the same kind of fixed-timer race. After 1 s the `fresh`
   scenario checks that `menu.py register` has finished. That has not been
   seen failing, and it would print a different message. Should it be fixed
   here or left alone?
4. Once this is fixed, should the #31 plan drop its rerun allowance in its
   own commit, or should this task do it?
