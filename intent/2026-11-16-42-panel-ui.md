# Intent: Panel UI tells you what is happening and reacts to the keys and mouse you expect

## Problem

The panel shows a lot of state, but several screens say the wrong thing, hide the right thing, or ignore an obvious input. All line numbers are from `main` at 6d42838 (1.0.0), checked in the current files.

**Status, errors and quota**

- **Errors and cooldown share the search placeholder.** The placeholder text is `root.filtering ? "Search repositories…" : root.cooldownText || root.error || ...` and is only visible while `searchField.text.length === 0` (`ActionsPanel.qml:291-294`). Type one letter and the error is gone. Focus the empty field and the placeholder becomes "Search repositories…" (line 292), so the error is gone too.
- **The footer shows the cooldown but never the error.** Line 374 is `root.cooldownText || "↑↓ move ..."`.
- **The global error is short-lived.** `s.error` is set on a failed reply (`Polling.js:184`) and cleared by any later successful reply (`Polling.js:200`). A failed repo can have its message wiped by an unrelated success before that repo recovers. The per-repo `r.error` is kept apart (`Polling.js:201`).
- **Rate-limit quota is read and thrown away.** `actions.py:142-145` parses `x-ratelimit-remaining` and `x-ratelimit-reset` into every reply. `Polling.js:176-177` uses them only to decide a back-off. Nothing stores or shows how many requests are left.

**Colours and labels**

- **Success and running look the same.** `statusColor` returns `Color.accent` for both `in_progress` and `success` (`ActionsPanel.qml:168`). Queued, cancelled, skipped and neutral fall through to plain text colour (line 169). The icons differ (`ActionsModel.js:17-24`), but only by shape.
- **The right-hand column shows raw API words.** Line 355 prints `modelData.status` as it is, so you read `in_progress`, `timed_out`, `startup_failure` and "awaiting final status" (`state()`, `ActionsModel.js:13-15`).
- **A repository whose last run failed says "0 running".** The repo status is `in_progress` or `neutral` only (`ActionsModel.js:47`). The info text is `active + " running"` (line 48). The recent runs are fetched (`actions.py:78-79`, `per_page=10`) and cached, but the repo row does not use their result. (Showing the last result on repo rows is the repo-health work in #43. This intent only covers how the row reads.)

**Run details**

- **The run subtitle spends its width on a fetch stamp.** It is `branch · #number · jobs fetched HH:MM:SS UTC · title` (`ActionsModel.js:62-64`). The subtitle is one elided line, so the title is the part that gets cut. The stamp is also the only sign of how old the job data is, so removing it needs an answer to question 10.
- **Useful fields are not shown.** `actions.py` passes whole run objects through (line 196), so `event`, `actor`, `head_sha`, `run_attempt` and timestamps reach the panel. The code reads `run_attempt` for polling (`Polling.js:90`, `:128`) but never shows it. Age and actor are not shown anywhere.
- **A step opens its job.** Step rows use `url: job.html_url` (`ActionsModel.js:78`), so pressing `o` on a step opens the job page, not the step.

**Search**

- **Every keystroke collapses the tree.** `onFilterTextChanged` sets `expanded = ({})` (`ActionsPanel.qml:36`). Open a repository, press `/`, type a branch name, and your open repository closes. Searching for a branch inside it is awkward.
- **Search looks broader than it is.** `rows()` matches repo name, description, run name, title, branch and state (`ActionsModel.js:39-43`) against cached runs only. Background checks fetch running runs for repositories you have not opened (`Polling.js:74-79`), so those can match. Finished runs of an unopened repository are not fetched until you select it, so a workflow that exists on GitHub may not match. The panel does not say this.

**Empty, loading and error states**

- **One empty message covers everything.** Line 366 is always "No matching repositories or workflows". It shows while discovery is still running, after an auth failure, with no repositories at all, and for a query with no match.
- **An expanded repository with no runs shows nothing.** After the repo row, `rows()` adds only run rows and the "more" row (`ActionsModel.js:49-65`). Nothing says "no runs". `rows()` also reads `(repo.runs || [])` (line 40), so "runs not loaded yet" and "no runs" look the same to the model.
- **Failed job fetches.** The message row says "Loading jobs…" when there is no detail yet and shows the error when there is one (`ActionsModel.js:67-68`). `detail.error` is set only for a permission error (`Polling.js:186-189`). Other failures set only `s.error` and `r.error`, so "Loading jobs…" can stay on screen. That is a polling-state bug, not a presentation one. It is listed under open question 10 so nobody assumes it is fixed here.

**Keys and mouse**

- **Right toggles an expanded row closed.** Right, `l`, Enter and Space all call `expand(false)`, which flips the row (`ActionsPanel.qml:246`, `:98-115`). README documents this. It is a choice, not a bug, but it does not match tree habits.
- **Modifiers are ignored.** The handler matches `event.key` only (lines 236-251). Ctrl+R refreshes, Shift+O and Ctrl+O open GitHub, Ctrl+J moves. The one modifier it reads is Shift on `r` (line 249).
- **Paging is a fixed 8 rows.** Lines 241-242 call `move(8)` and `move(-8)`. Row heights differ (line 314: a taller row with a subtitle, a shorter one without), so a page is not a screenful.
- **Clicking a row does nothing.** The delegate (`ActionsPanel.qml:309-359`) has no `MouseArea` or other pointer handler. Wheel scrolling comes from `ListView`.
- **No copy or help key.** Nothing copies a row's link, and no in-panel key opens help. Home and End already jump to the first and last row (lines 243-244), so first/last needs nothing new. There is no report of an unmet need for the other extra keys, so they are an open question (7), not a goal.

**Accessibility**

- **Rows have no accessible name, role or state.** No `Accessible.*` property appears in `ActionsPanel.qml`. The selected row is `root.cursor` and a background colour (line 315), not a focused item. The search field has no label other than the placeholder that goes away when you type. Whether Quickshell exposes these to a screen reader on this setup has not been tested.

## Proposed outcome

Only what holds whichever way the open questions go.

- **Errors stay visible while you type.** With a failed fetch, the error text is still on screen after you type a character in the search field and while the field is focused. The time a GitHub pause ends is visible the same way.
- **Success and running can be told apart at a glance.** In the same panel, a successful run and a running run no longer share one colour. Each status shows a short plain label ("failed", "running", "queued", "timed out"), not the raw API string.
- **A run row shows more than branch and number.** The run subtitle includes the event, the actor and the age of the run, and the title is not the first thing to be cut. The job-fetch timestamp is gone from that line only if question 10 gives the age of job data another place.
- **Search keeps your place.** Typing a filter does not close the repositories you opened, at least those that still match (question 6). The panel states that search covers only the runs already loaded.
- **Each empty screen says why.** The panel tells apart: still discovering, a GitHub or auth error, no repositories, no match for the filter, and an expanded repository confirmed to have no runs. It does not say "no runs" for a repository whose runs have not loaded.
- **Keys and mouse are documented and consistent.** Page keys move one screenful of rows. Ctrl and Alt combinations that the panel does not use are left alone. A click does what question 3 decides. The key sheet and README list every key that works.
- **`o` on a step opens that step** on GitHub, or the owner decides otherwise (question 8).
- **Rows can be named to assistive technology** with their kind, title and status, if Quickshell exposes this (question 11).
- **No new GitHub requests.** The panel makes no more calls than today.

## Affected users and systems

- Anyone who opens the panel on an Omarchy desktop. The visible changes are in every row.
- Screen-reader users, if Quickshell exposes the properties.
- Files: `ActionsPanel.qml`, `ActionsModel.js`, `Polling.js` (error and quota handling), `actions.py` (cleaning any new text fields), `keybindings.sh` and `README.md` (key lists). `flake.nix` (`passthru.runtimeDeps`) and `README.md:23` and `:62` (package lists) are affected only if a new runtime command is chosen in question 7.
- Tests: `tests/model.cjs`, `tests/polling.cjs`, `tests/test_actions.py`, `tests/qml-smoke.py`.
- Neighbours: #43 (repo-level health: last-run result on repo rows) shares `ActionsModel.js:46-48` and the status colours. #30 already added the "more" row (`ActionsModel.js:51-58`), and #30 and #23 share the rebuild path (`rebuild()` runs every second, `ActionsPanel.qml:41`), so anything added to rows must stay cheap.

## Constraints

Kept as they are:

- **No daemon, no stored data.** Anything shown about quota is only the last value read from a response, held in memory. Nothing is written to disk. No token handling.
- **Theme-native.** Every colour, font and spacing comes from the Omarchy theme (`Color.*`, `Style.*`). No hard-coded colours.
- **Keyboard-first.** Every action stays reachable by keys. Mouse and accessibility are additions, not replacements.
- **No shell strings.** Any new command the panel starts is run with the same safe style as `xdg-open` now (`ActionsPanel.qml:171-174`).
- **Untrusted GitHub text is sanitised (#32).** `actions.py:42` cleans only `name`, `display_title` and `head_branch` for runs (and `name` for jobs and steps, lines 192 and 195). `actor`, `event` and `head_sha` are not cleaned today. Any new field the panel shows must be cleaned first, and the panel keeps `textFormat: Text.PlainText`.
- **github.com is pinned (#32).** Any new link passes `Model.browsable()` (`ActionsModel.js:10`).
- **API budget unchanged.** If a field is not in the data already fetched, it is not shown.
- **Fast rebuild.** Row text rebuilt every second must stay cheap, and new row fields must repaint when they change (`shownFields`, `ActionsModel.js:93`).

Bent:

- **"Keyboard-first, no buttons"** is bent only if the owner chooses mouse actions beyond selecting (question 3).
- **Existing key behaviour may change** if question 4 changes Right. That affects anyone who learned the documented behaviour.
- **A new runtime command** may be needed if the owner picks a copy key (question 7).

## Open questions

1. **Where do status, errors and quota show?** The owner decides whether they get their own always-visible line, share the footer, or stay in the search area, and which of error, pause end, progress and quota are shown at all. Is the quota worth showing at all?
2. **How much run detail, and where?** Which fields (event, actor, age, SHA, attempt) go on the run row, and which, if any, appear only for the selected row or on demand.
3. **What does a click do?** Select only, select and toggle, or something else?
4. **What does Right do on an open row?** Keep it toggling (documented today), or follow tree habits and enter the row?
5. **Filter and expansion.** While a filter is active, do expanded repositories that no longer match disappear (state kept for when the filter clears), or stay visible?
6. **Search coverage.** Is a fixed note that search covers loaded runs enough, or should the panel show how many repositories have run data yet?
7. **Extra keys.** Does the owner want any of: copy a row's link, a help key, a quit key, and Ctrl-d/Ctrl-u paging? Which, if any, are in this task? For a copy key, what happens when the needed command is missing?
8. **Step link.** Is there a stable GitHub link to a single step, or should `o` on a step keep opening the job?
9. **Colours.** If the theme has no distinct success colour, does the panel use another theme colour, rely on shape and label, or accept a mix that may not follow the theme?
10. **Stale or failed job data.** Should the age of the job snapshot stay visible somewhere once it leaves the subtitle? Is the "Loading jobs…" after a failed fetch, and expanded runs that stop updating when you select something else, fixed here or by the polling intent that owns them?
11. **Accessibility testing.** There is no screen-reader test setup in the repo. Is it enough to set the Qt properties and cover them in the QML smoke test, or does the owner want a manual check recorded?
12. **Order against #43.** Should this land after #43, so the status colours and repo-row labels are changed once, or before, with #43 reusing them?
