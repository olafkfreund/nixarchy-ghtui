# Intent: CI catches keyboard and layout regressions in the panel

## Problem

`nix flake check` is the only check CI runs (`.github/workflows/check.yml:21`).
It never starts the panel.

What the check does with the QML smoke test:

- `flake.nix:80-83` runs `tests/qml-smoke.py` once, against a plugin
  directory that does not exist. It only confirms that the script rejects
  a missing directory and prints the expected message.
- The real scenario (the fake helper, the panel, `quickshell`) never runs
  in CI. `tests/qml-smoke.py:16-17` needs `OMARCHY_PATH` and a live Omarchy
  theme in `~/.local/state/omarchy`. The check's sandbox has neither (it
  sets `HOME` to an empty directory, `flake.nix:73-74`).
- The scenario has been run by hand on the razer host (#36). Nothing
  re-runs it when the code changes. The README says the same
  (`README.md:205-207`).

What the scenario checks when it does run:

- Keys are not sent as key events. The test calls `panel.move(1)` and
  `panel.expand(...)` directly (`tests/qml-smoke.py:100-121`).
- The key handler is in `ActionsPanel.qml:234-255` (`Keys.onPressed` on
  the `keys` item) and `ActionsPanel.qml:275-285` (the search field).
  Nothing tests it. That covers focus, `/` moving focus to the search
  field, and Escape. In the list Escape clears the filter and then closes
  the panel; in the search field it clears the filter and returns focus
  to the list. It also covers plain and Shift+R, which start two
  different refreshes (`Polling.js:41-42`).
- Nothing tests layout. The rows are drawn by the `ListView` and its
  delegate (`ActionsPanel.qml:302-314`). The list height can be zero and
  clips its rows (`:305-306`). The test reads `panel.entries` and
  `panel.status()`, not what is on screen.
- The process lifecycle is only partly covered. The smoke test closes and
  reopens the panel in quick succession (`tests/qml-smoke.py:135-147`).
  It never checks a helper that fails to start
  (`ActionsPanel.qml:144-151`, `onRunningChanged` at `:202`). It does not
  check a helper that is still running when the panel closes. The Python
  tests cover cancellation of `gh`, not the QML side.

So a change that breaks a key, the focus handover, or the row layout, can
leave every check green. The owner finds out after a rebuild on a real
desktop.

## Proposed outcome

- A push or pull request that breaks keyboard handling, or hides or
  collapses the rows, turns CI red with a message that names what broke.
- The graphical smoke test (or a smaller test that does the same job) runs
  in CI on every push and pull request. It does not need the owner's
  desktop.
- The test drives the panel with key presses, not direct method calls. For
  each of these it fails when the behaviour changes: moving the selection,
  expanding and collapsing a row, moving focus to the search field,
  Escape in the list and in the search field, and both kinds of refresh.
- The test fails when a seeded row cannot be reached by keyboard and seen
  inside the panel. Passing needs more than a nonzero row height.
- A helper that fails to start, and a panel closed while a request is
  running, each end in a state the test checks (no stuck busy state, no
  further requests).
- A failing run says which stage failed, as #36 already made it do.
- Repeat runs on the same commit give the same result. #36 improved the
  failure messages. It did not explain the p620-only failures, so this
  task must not rely on that being solved.

## Affected users and systems

- The owner and anyone who sends a pull request. CI becomes slower and
  gains a new way to fail.
- Files: `.github/workflows/check.yml`, `flake.nix` (`checks.plugin`),
  `tests/qml-smoke.py`, and `README.md` (its "runs only locally"
  statements go stale). The panel source may need changes to be testable
  (see open question 2).
- Hosts: GitHub-hosted `ubuntu-latest` runners. razer and p620 are not
  needed once this lands. Today only razer can run the test (#36).
- Not affected: users of the plugin. No runtime behaviour changes.

## Constraints

- The shipped plugin keeps its design: no daemon, no token storage,
  theme-native, keyboard-first, argument arrays not shell strings,
  github.com pinned (#32), untrusted GitHub text sanitised (#32). This task
  bends none of them. It adds tests and CI only.
- The fake helper stays fake. CI must make no request to GitHub and use no
  token or secret. The workflow keeps `permissions: contents: read`
  (`check.yml:7-8`).
- The panel talks to `Quickshell` and Omarchy `Commons`/`Ui`
  (`tests/qml-smoke.py:21-22`). CI needs Omarchy's shell code and a theme
  from somewhere. That source must be pinned, not fetched at run time from
  a moving branch. Any new pinned dependency is a supply-chain cost the
  owner must accept (open question 1).
- Actions in `check.yml` are pinned by commit SHA. Any new action follows
  the same rule.
- The 15 minute job limit (`check.yml:17`) stays unless the owner raises
  it. The smoke test's own timeouts (`tests/qml-smoke.py:70,157`) are not
  widened to hide flakiness.
- The test must not depend on the owner's display or session.
- Test input must never reach the owner's desktop when the test runs
  locally.
- Existing tests keep passing. `nix flake check` on p620 (no desktop)
  must still work, or the graphical test must be a separate, named check.

## Open questions

1. How faithful to the real Omarchy shell must CI be? A copy of the real
   code catches theme API drift. A stand-in is cheaper but can hide the
   very breaks the test should catch. Which does the owner accept, and
   what pinned source is acceptable?
2. How faithful must key delivery be? The panel takes exclusive keyboard
   focus from the compositor (`ActionsPanel.qml:214`). Must CI cover that
   focus handover, or is it enough to test the key handlers, with the
   focus handover checked by hand before a release? Is changing the panel
   source to make keys testable acceptable?
3. Does the graphical test run inside `nix flake check`, or as a separate
   job? A separate job keeps `flake check` fast and usable on p620, but
   two places must stay in step.
4. What counts as a layout failure? The owner must pick the line: rows
   missing or unreachable, rows overlapping, text cut off, or a match
   against a stored image. A stored image is the most thorough but breaks
   whenever the theme or fonts change.
5. Should the old "missing directory" check at `flake.nix:80-83` stay once
   the real test runs? It costs nothing and covers the argument parsing.
6. #36 forbids reruns of the smoke test and the unit tests
   (`spec/2026-09-24-36-smoke-flake.md:106-108`). Does that rule still
   hold here? Allowing a retry for the graphical job would change that
   policy, so it needs the owner's explicit decision.
